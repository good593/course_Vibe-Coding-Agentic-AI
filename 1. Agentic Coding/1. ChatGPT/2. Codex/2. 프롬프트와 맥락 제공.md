# 1. 프롬프트와 맥락 제공

## 같은 기능 요청을 검증 가능한 작업으로 바꾸기

시작: 0장 상품 조회와 기본 테스트 통과

결과: 건강 고민 입력 → 최대 5개 추천 → 추천 근거 표시

해당 요구사항: RF-1.1, RF-1.2, RF-1.3

---

## 먼저 경험할 문제

“추천 기능을 만들어 줘”에는 많은 결정이 빠져 있습니다.

- 어떤 데이터로 연결할까요?
- 몇 개를 어떤 순서로 보여줄까요?
- 입력이 비어 있거나 검색 결과가 없으면요?
- 어떤 결과를 보면 완료라고 할 수 있을까요?

짧은 요청이 잘 처리되어도, 추측한 조건을 확인해야 합니다.

---

## 단계 1. 변경 전 상태 확인

터미널에서 실행합니다.

```powershell
uv run --locked python -m pytest -q
git status --short
```

`project/README.md`와 다음 코드를 엽니다.

`backend/api/products.py` → `services/products.py`
→ `repositories/products.py` → `db/schema.sql`

---

## 단계 2. 짧은 요청으로 해석 확인

Codex의 새 채팅에 입력합니다.

```text
건강 고민을 입력하면 영양제를 추천하는 기능을 추가하고 싶어.
아직 코드는 수정하지 말고, 네가 이해한 입력·처리·출력과
구현하기 전에 확인해야 할 조건을 설명해줘.
```

답변에서 **요청에 없는 조건을 추측한 부분**을 표시합니다.
이미 정확하게 물어봤다면 그것도 좋은 결과로 기록합니다.

---

## 단계 3. 사용할 맥락 지정

Codex에 파일 경로를 전달합니다. `@`로 선택할 수 있으면 선택합니다.

```text
../docs/요구사항정의서.xlsx와 ../docs/데이터 정의서.xlsx,
../docs/실습 보완 명세.md의 추천 규칙을 읽어줘.
CSV 3개의 실제 컬럼과 db/schema.sql도 대조해줘.
Excel을 읽는 데 도구가 필요하면 uv 환경의 읽기 도구를 사용해줘.
원본 파일은 수정하지 말고 RF-1.1~1.3의 조건만 정리해줘.
아직 구현하지 마.
```

파일을 읽지 못했다면 추정 요약을 받지 말고 경로·읽기 오류를 해결합니다.

---

## 이번 장의 API 계약

`POST /api/recommendations`

```json
{"concern": "피로"}
```

```json
{"items": [{"product_id": "P001", "name": "상품명",
  "reasons": [{"nutrient": "비타민 C", "functionality": "항산화"}]}]}
```

예시는 응답 형식입니다. 실제 상품과 근거는 CSV 관계를 조회합니다.

---

## 단계 4. 목표와 맥락을 명시

앞 단계에 이어 아래 요청을 입력합니다.

```text
[목표]
RF-1.1~1.3의 추천 API와 Streamlit 입력·결과 화면을 구현해줘.
[맥락]
상품 조회의 API→서비스→저장소 구조를 참고해줘.
추천 규칙은 ../docs/실습 보완 명세.md를 따라줘.
nutrient_functions.concern과 keyword로 입력을 찾고,
nutrient를 products.ingredient_keyword에 연결해줘.
응답은 items 배열과 상품별 reasons 배열을 사용해줘.
```

아직 전송하지 않고 다음 슬라이드의 조건을 이어 붙입니다.

---

## 단계 5. 제약과 완료 조건 추가

```text
[제약]
SQL은 저장소 계층, 추천 규칙은 서비스 계층에 둬.
Groq는 호출하지 말고 데이터에 있는 근거만 사용해줘.
기존 상품 API와 CSV 원본을 유지해줘.
[완료 조건]
선택 목록과 직접 입력을 모두 지원한다.
앞뒤 공백은 제거하고 빈 입력은 422를 반환한다.
부분 문자열 추측 대신 정해진 concern/keyword 일치 규칙을 쓴다.
상품ID 중복 없이 정렬해 최대 5개를 반환한다.
근거가 여러 개면 reasons에 모으고, 매칭이 없으면 items=[]이다.
기본 테스트와 신규 테스트, Ruff 검사를 실행해 결과를 보고해줘.
```

---

## 단계 6. 실행 결과 확인

백엔드와 화면을 실행한 후 `/docs`에서 추천 API를 호출합니다.

| 입력·조건 | 기대 결과 |
| --- | --- |
| `피로` | 데이터에서 연결된 상품과 근거 표시 |
| ` 피로 ` | 공백 없는 입력과 동일 |
| 빈 문자열·공백만 입력 | 422 |
| 매칭되지 않는 문자열 | 200, 빈 배열 |
| 후보가 7개인 테스트 데이터 | 5개, 상품ID 오름차순 |
| 같은 상품에 근거 2개 | 상품 1개와 근거 2개 |

원본에 없는 사례는 테스트 내부의 합성 데이터로 검증합니다.

---

## 단계 7. 결과가 다를 때 수정 요청

```text
추천 결과에서 같은 상품이 두 번 나타났어.
입력은 '피로'이고 중복된 상품ID는 [직접 확인한 ID]야.
상품은 한 번만 반환하고 근거는 reasons에 모아야 해.
재현 테스트를 먼저 추가하고 원인을 수정해줘.
기존 정상 사례도 함께 검증해줘.
```

대괄호는 관찰한 값으로 바꿉니다. 확인하지 않은 오류는 만들지 않습니다.
