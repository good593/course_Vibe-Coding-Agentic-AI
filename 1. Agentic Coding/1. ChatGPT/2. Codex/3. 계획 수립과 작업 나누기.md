# 2. 계획 수립과 작업 나누기

| 상황 | 권장 방식 |
|---|---|
| “이 함수의 dtype 오류를 고쳐줘” | 좋은 프롬프트로 바로 실행 |
| “기존 RAG를 하이브리드 검색으로 개편해줘” | Plan으로 영향 범위와 순서를 확인한 뒤 실행 |

즉, 좋은 프롬프트는 무엇을 원하는지 명확히 하고, Plan 모드는 그 목표를 어떻게 구현할지 중간에 검토하는 장치입니다.

---
## 사용자 조건 저장을 구현하기 전에

시작: 1장 추천 API·화면·테스트 통과

결과: 사용자 조건 저장과 SQLite 변경 계획

이번 장은 **계획 검토까지** 진행하고, 3장에서 구현합니다.

---

## 먼저 경험할 문제

“사용자 정보를 저장해 줘”는 한 파일의 변경이 아닙니다.

입력 항목 → DB 테이블 → API → 화면 → 기존 데이터 → 테스트

현재 데이터 정의서에는 사용자 정보가 작성 예정으로 남아 있습니다.
빈 부분을 AI가 임의로 확정하기 전에 질문과 결정을 남깁니다.

---

## 단계 1. 계획 모드 선택

Codex 입력창의 모드 선택에서 **Plan**을 선택합니다.
설치 버전에 해당 선택이 없으면 다음 문장을 먼저 입력합니다.

```text
이번 요청은 계획 검토 단계야. 파일을 수정하거나 명령으로
DB를 변경하지 말고 조사·질문·계획 제안만 해줘.
```

UI 모드 이름은 설치 버전에 따라 확인합니다.
CLI의 단축키가 IDE에서도 동일하다고 가정하지 않습니다.

---

## 단계 2. 영향 범위 조사 요청

```text
사용자 조건을 저장하고 다음 접속 때 불러오는 기능을 계획해줘.
../docs/실습 보완 명세.md의 사용자 프로필 결정을 참고하고,
현재 SQLite 스키마, Settings, API, 화면, 테스트를 조사해줘.
불명확한 조건은 최대 3개씩 질문해줘.
추가/수정할 파일과 기존 데이터에 미칠 영향을 먼저 설명해줘.
코드와 DB는 아직 변경하지 마.
```

프로젝트 자료와 조사한 코드 경로가 답변에 포함되는지 확인합니다.

---

## 단계 3. 이번 실습의 결정 제공

```text
수업용 프로필은 가상 사용자만 사용해.
profile_id는 서버가 생성하고, age_group/sex/pregnancy/lactation을 저장해.
회원 인증과 상담 이력은 9장에서 구현하며 지금은 완료로 표시하지 마.
SQLite 기존 상품 44개와 기능성·섭취기준 데이터를 보존해야 해.
요청과 검증 규칙은 실습 보완 명세의 프로필 항목을 따라줘.
이 결정을 반영해 계획을 보완해줘.
```

수업용 추가 결정과 원본 요구사항을 구분해 기록합니다.

---

## 단계 4. DB 변경 전략 비교

Codex에게 두 접근의 차이를 설명하게 합니다.

```text
schema.sql만 수정하고 init_db를 다시 실행하는 방법과,
이미 존재하는 DB에 버전별 변경을 적용하는 방법을 비교해줘.
현재 CREATE TABLE IF NOT EXISTS가 기존 컬럼을 바꾸는지도 확인해줘.
실행은 하지 말고, 데이터 보존과 재실행 관점에서 설명해줘.
```

기존 DB에 대한 **명시적 마이그레이션**이 필요한 이유를 확인합니다.

---

## 단계 5. 계획 문서 작성 요청

모드가 쓰기를 제한한다면 계획 검토 후 일반 작업 모드로 돌아옵니다.

```text
지금까지 합의한 내용만 docs/plans/02-profile-migration.md에 저장해줘.
목표, 제외 범위, API 계약, 파일별 변경, 데이터 보존,
백업/복구, 구현 순서, 테스트와 완료 기준을 포함해줘.
아직 구현하지 말고 계획 파일만 작성해줘.
```

`PLANS.md`는 반드시 필요한 특별 파일이 아닙니다.
반복해서 쓸 계획 형식이 필요할 때 별도로 표준화합니다.

---

## API 계약과 검증 대상

| API | 동작 |
| --- | --- |
| `POST /api/profiles` | 유효한 조건 저장, 201과 profile_id 반환 |
| `GET /api/profiles/{profile_id}` | 저장 조건 조회, 없으면 404 |

프로필 값은 기준표에 존재하는 조합인지 검사합니다.

- 비어 있는 필수 값 또는 없는 조합: 422
- 상품 목록 API와 추천 API: 기존 동작 유지
- DB 변경 명령 재실행: 중복 테이블·레코드 없이 성공

---

## 단계 6. 계획 검토

| 확인할 항목 | 계획에 있어야 할 내용 |
| --- | --- |
| 변경 범위 | 파일과 수정 이유 |
| 순서 | 백업 → 마이그레이션 → API → 화면 → 검증 |
| 데이터 보존 | 기존 레코드의 값·개수 비교 |
| 실패 대응 | 트랜잭션과 백업 복구 절차 |
| 완료 조건 | 새 기능과 기존 기능의 검증 |

“DB 초기화로 해결”처럼 데이터를 잃을 수 있는 계획은 수정합니다.

---

## 단계 7. 세션을 나눠 인계

```text
다음 채팅에서도 이어갈 수 있게 계획 파일 끝에 인계 메모를 추가해줘.
합의한 결정, 미해결 질문, 관련 파일, 다음 작업을 적어줘.
실행하지 않은 테스트는 미실행이라고 적어줘.
```

새 채팅에서 계획 파일을 지정하고 요약하게 합니다.
이전 대화 전체 없이도 같은 작업을 시작할 수 있는지 비교합니다.

---

## 완료 체크와 다음 시작 상태

- [ ] 모호한 조건을 질문과 결정으로 분리했다.
- [ ] SQLite 기존 데이터를 지키는 계획이 있다.
- [ ] API 계약과 테스트가 계획에 포함된다.
- [ ] 새 채팅에서 계획을 이어갈 수 있다.
- [ ] 애플리케이션 코드는 아직 1장 완료 상태다.

계획 문서만 커밋합니다. 다음 장에서 규칙을 만든 뒤 구현합니다.
