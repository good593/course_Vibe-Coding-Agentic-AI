# 4. Plan 모드로 구현 방법 검토하기

## 합의한 요구사항을 구현 가능한 작업으로 나누기

시작: 3장 요구사항 문서·지침·Skill 준비

결과: 구현 계획 + 검증·커밋·PR 순서

---

## 요구사항과 구현 계획의 차이

| 문서 | 다룰 질문 |
| --- | --- |
| 요구사항 | 누구에게 어떤 동작을 제공할 것인가? |
| 구현 계획 | 어느 파일을 어떻게 바꾸고 검증할 것인가? |

“근거가 없으면 생성기를 호출하지 않는다”는 완료 조건입니다.
“검색 결과 확인 후 생성기로 전달한다”는 구현 순서입니다.
요구사항을 다시 길게 복사하기보다 구현 결정을 기록합니다.

---

## 단계 1. 시작 상태 확인

project 터미널에서 확인합니다.

```powershell
# 준비 브랜치와 커밋을 확인합니다.
git status --short --branch
git log -3 --oneline
# 앱은 아직 상품 조회 시작 코드 상태입니다.
uv run --locked python -m pytest -q --basetemp=.pytest_cache/tmp
```

요구사항을 정리하는 과정에서 앱 코드가 바뀌었다면 먼저 이유를 확인합니다.
근거 문서의 준비·검수 상태와 미결 질문도 다시 확인합니다.

---

## 단계 2. Plan 모드 선택

현재 VS Code Codex의 모드 선택에서 Plan을 찾습니다.
CLI에서는 지원되는 경우 /plan 또는 Shift+Tab으로 전환합니다.

```text
구현 전에 조사와 계획만 수행해줘.
요구사항을 확인하고 불명확한 부분은 질문해줘.
파일별 변경·구현 순서·검증·커밋 단위를 제안해줘.
아직 애플리케이션 코드는 수정하지 마.
```

Plan UI가 없으면 같은 요청으로 조사·계획을 구분합니다.
모드 사용 여부와 실제 수행한 작업을 기록합니다.

---

## 단계 3. 실제 코드의 연결 지점 조사

```text
docs/requirements/rag-chatbot.md와 ../docs/실습 보완 명세.md를 읽고
현재 backend/main.py, backend/config.py, backend/integrations/llm.py,
frontend/api_client.py와 frontend/app.py, tests/conftest.py를 조사해줘.
문서 검색→생성→인용 검증→API→화면의 책임을 배치해줘.
실제로 있는 파일과 새로 만들 파일을 구분하고
기존 상품 API·SQLite를 보존하는 이유를 설명해줘.
아직 구현하지 마.
```

기존 구조와 연결 지점을 활용할 수 있는지 확인합니다.

---

## 단계 4. 검색 방법 비교

| 후보 | 확인할 점 |
| --- | --- |
| 태그·키워드 검색 | 문서 규모, 결정적인 결과, 구현·테스트 용이성 |
| 전문 검색·벡터 검색 | 추가 의존성, 인덱스, 자료·비용·운영 필요성 |

```text
첫 버전에 필요한 검색 방법을 비교하고 최소한의 방법을 추천해줘.
정규화·매칭·동점 정렬·최대 3개·공식 검수 필터를 고정해줘.
합성 fixture의 기대 결과와 규칙이 일치하는지도 확인해줘.
```

선택한 검색 규칙과 한계를 계획에 남깁니다.

---

## 단계 5. 생성과 인용 검증 계획

```text
현재 TextGenerator를 확장해 상담에 연결할 방법을 제안해줘.
질문과 비신뢰 문서 본문을 구분하는 프롬프트,
JSON 생성 결과 파싱, 선택 문단 ID 검사, 서버 출처 구성을
계획해줘. 빈 결과·없는 인용·검색에서 선택하지 않은 인용·
API 장애·문단은 있지만 답을 못 하는 경우도 포함해줘.
실제 호출과 모의 테스트를 분리하고 코드 수정은 하지 마.
```

고정 연결 응답을 실제 상담 구현으로 오해하지 않습니다.
ID 검증과 답변의 의미 대조를 모두 계획합니다.

---

## 단계 6. 테스트와 화면 계획

| 검증 대상 | 계획에 포함할 사례 |
| --- | --- |
| 입력·검색 | 공백·초과·매칭·무매칭·정렬·필터 |
| 생성·인용 | 정상·부족·파싱 실패·없는/선택하지 않은 ID |
| 화면 | 답변·출처·장애·기존 상품 페이지 이동 |
| 보존 | 기존 22개 테스트·상품 44개·DB/CSV 미변경 |

fixture는 테스트에만 주입합니다.
실제 자료가 없으면 공식 문서 준비를 구현 전 작업으로 넣습니다.

---

## 단계 7. 작은 구현·커밋 단위로 나누기

아래는 시작 예시입니다. 학생 계획의 의존성과 검증에 맞춰 조정합니다.

| 단위 | 결과 | 검증 | 커밋 예시 |
| --- | --- | --- | --- |
| 1 | 문서 로딩·필터·검색 | 단위 테스트 | feat: retrieve reference passages |
| 2 | 생성·인용·상담 API | 모의 생성·API 테스트 | feat: add grounded chat API |
| 3 | 화면·연결·실행 안내 | 화면·전체 테스트 | feat: connect chat UI |

첫 실습은 feature 브랜치의 여러 커밋을 하나의 PR로 묶을 수 있습니다.
각 커밋에서 무엇을 검증했는지 설명할 수 있어야 합니다.

---

## 다음 장의 Skill이 읽을 검증 계획

| 계획에 적을 내용 | 5장에서 사용할 곳 |
| --- | --- |
| 단위별 완료 조건·테스트 경로·명령 | verify-changes |
| 변경 파일·커밋 범위와 검증 기록 경로 | commit-changes |
| 전체 검증·리뷰·base/head·PR 범위 | create-pr |

구현은 그때의 상황에 맞는 프롬프트로 요청합니다.
Skill은 계획의 검증·커밋·PR 절차를 반복 수행합니다.
실행하지 못한 검증과 재실행 조건도 계획에 남깁니다.

---

## PR을 여러 개로 나눌 때

```text
계획의 작업을 독립적으로 검토 가능한 커밋으로 나눠줘.
단일 PR과 여러 PR의 장단점, 각 PR의 의존성을 설명해줘.
여러 PR이면 base/head와 앞 PR 병합 후 다음 브랜치 시작 순서까지
계획해줘. 관련 없는 구조 변경은 별도 작업으로 분리해줘.
```

이번 수업의 기본은 **하나의 feature 브랜치·하나의 RAG PR**입니다.
준비 문서·설정은 기능 구현을 시작하기 전에 기준 main에 반영합니다.

---

## 단계 8. CI 경로와 실행 준비 계획

Git 루트는 docs·data·project를 포함하는 학생 실습 폴더입니다.

```text
../docs/templates/ci.yml을 읽고 이 Git 루트에 맞게 적용할
위치와 검증 방법을 계획해줘. .github/workflows/ci.yml은
Git 루트에, uv 명령의 working-directory는 project에 둬.
전체 docs와 data를 checkout하고 기본 CI는 키 없이 동작하게 해줘.
아직 workflow나 앱을 작성하지 마.
```

기존 CI가 있으면 중복 생성 대신 필요한 변경을 계획합니다.

---

## 단계 9. 계획 검토와 저장

구현·테스트·실패 처리·커밋 순서를 읽고 계획을 확인합니다.
쓰기 제한이 있으면 일반 작업 모드로 돌아와 요청합니다.

```text
검토한 계획만 docs/plans/rag-chatbot.md에 작성해줘.
../docs/templates/rag-plan.md 형식을 사용해줘.
새 채팅에서도 이어갈 수 있게 합의·미결 질문·관련 파일·
다음 구현 단위·실행하지 않은 검증을 포함해줘.
아직 애플리케이션을 구현하지 마.
```

Plan 모드에서 계획 파일을 쓰지 못한 것을 기능 실패로 판단하지 않습니다.

---

## 단계 10. 준비 문서 커밋과 기준 정리

실제 작성한 계획과 기록만 선택합니다.

```powershell
# 계획 문서를 stage하고 확인합니다.
git add -- docs/plans/rag-chatbot.md
git diff --cached
git diff --cached --check
# 검토한 계획을 커밋합니다.
git commit -m "docs: plan RAG implementation and delivery"
```

미커밋 준비 파일은 먼저 정리합니다. 5장에서 준비 브랜치를
main에 fast-forward한 뒤 feature 브랜치를 시작합니다.
