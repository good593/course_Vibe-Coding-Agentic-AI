# 5. 검증과 코드 리뷰

## SQLite에서 PostgreSQL로 전환하기

시작: 3장 프로필과 SQLite 마이그레이션 완료, 4장 설정 확인

결과: 기존 데이터와 API를 유지하는 DB 전환 + 검증 보고서

---

## 먼저 경험할 문제

“PostgreSQL로 변경 완료”라는 답변만으로는 알 수 없습니다.

- 기존 데이터는 전부 옮겨졌을까요?
- NULL·한글·조건이 붙은 수치가 보존됐을까요?
- 화면과 추천 순서는 그대로일까요?
- 실제 PostgreSQL에서 실행한 테스트일까요?

코드 검사, 동작 테스트, 데이터 대조, 리뷰를 함께 사용합니다.

---

## 단계 1. 변경 전 기준 확보

```powershell
uv run --locked python -m pytest -q
uv run --locked python -m scripts.backup_db
git status --short
```

백업 명령은 3장에서 만든 것을 사용합니다.
SQLite 백업 파일과 상품/프로필 조회 응답을 보관합니다.
기존 데이터의 행 수·주요 값과 현재 커밋 해시를 기록합니다.

---

## 단계 2. 먼저 검증 계획 요청

```text
SQLite에서 PostgreSQL로 전환할 계획을 세워줘.
API 계약과 Streamlit 동작은 유지하고 SQLite 실행도 계속 지원해.
현재 SQL과 연결 코드를 조사하고 변경 영향을 설명해줘.
기존 DB의 값을 빠짐없이 대조할 검증 방법, 새 ID 생성,
NULL·한글·트랜잭션·실패 후 복구를 계획에 포함해줘.
아직 코드를 바꾸지 말고 docs/plans/05-postgres.md에 정리해줘.
```

---

## 단계 3. PostgreSQL 실행 환경 준비

Docker를 사용할 경우 아래 명령으로 준비 여부를 확인합니다.

```powershell
docker --version
docker compose version
```

Docker Desktop을 실행합니다. 설치가 어렵다면 강사가 제공한
실습용 PostgreSQL 연결을 사용합니다. 개인별 DB를 분리합니다.

PostgreSQL 없이 SQLite만 테스트했다면 DB 전환 완료가 아닙니다.

---

## 단계 4. Compose 파일 작성 요청

```text
PostgreSQL 17을 위한 compose.yaml을 작성해줘.
서비스 이름은 db, DB명은 healthy_day, 사용자명은 lab으로 해줘.
127.0.0.1:5433만 노출하고 named volume으로 데이터를 보존해줘.
비밀번호는 .env의 POSTGRES_PASSWORD를 참조하고 값이 없으면 실패하게 해줘.
pg_isready 헬스체크를 넣어줘. 아직 컨테이너는 실행하지 마.
.env.example에는 값 없는 설정 이름과 설명만 추가해줘.
```

`.env`에 실습용 비밀번호를 직접 설정합니다.

---

## 단계 5. 서버 시작과 준비 확인

```powershell
docker compose up -d db
docker compose ps
docker compose exec db pg_isready -U lab -d healthy_day
```

서버가 준비되면 `.env`에 다음 연결값을 작성합니다.

```dotenv
DATABASE_URL=postgresql+psycopg://lab:본인의_비밀번호@127.0.0.1:5433/healthy_day
```

특수문자는 URL 인코딩하거나 코드에서 URL 객체로 구성합니다.
연결 문자열 전체를 로그나 채팅에 출력하지 않습니다.

---

## 단계 6. Codex에게 구현 맡기기

```text
검토한 05-postgres 계획을 구현해줘.
uv add로 SQLAlchemy 2 계열과 psycopg[binary]를 추가하고 lock을 갱신해줘.
Settings에 DATABASE_URL을 추가하되 없으면 기존 DATABASE_PATH를 써줘.
SQL과 트랜잭션은 DB/저장소 계층에서 처리해줘.
서비스와 API 계약은 유지하고 SQLite/PostgreSQL 양쪽을 지원해줘.
SQLite 백업을 읽어 비어 있는 PostgreSQL로 옮기는 스크립트를 만들어줘.
DB 초기화나 데이터를 지우는 방식으로 전환하지 마.
```

---

## 단계 7. 이관 스크립트의 계약 고정

```text
scripts/migrate_postgres.py에 --dry-run과 --apply를 제공해줘.
SOURCE_SQLITE_PATH와 DATABASE_URL은 설정에서 읽어줘.
dry-run은 원본/대상 상태와 예상 건수만 읽고 DB를 변경하지 않아야 해.
apply는 대상이 비어 있을 때만 실행하고, 중간 실패를 롤백해줘.
기존 테이블 데이터와 프로필, 적용 이력을 모두 고려해줘.
이미 데이터가 있으면 덮어쓰지 말고 명확히 중단해줘.
명시적 ID를 이관했다면 다음 자동 생성 ID가 충돌하지 않게 해줘.
```

`SOURCE_SQLITE_PATH`에는 3장에서 만든 백업 경로를 설정합니다.

---

## 단계 8. 이관 계획을 확인하고 적용

구현된 스크립트를 읽고 다음 순서로 실행합니다.

```powershell
uv run --locked python -m scripts.migrate_postgres --dry-run
uv run --locked python -m scripts.migrate_postgres --apply
```

대상 DB 이름과 예상 건수를 확인한 뒤 두 번째 명령을 실행합니다.
dry-run은 데이터 검증을 대체하지 않습니다.
적용 결과를 `docs/reports/05-migration.md`에 남깁니다.

기본 테스트는 API 키 없이 동작하게 유지해줘.

## 대조할 항목

| 검증 | 완료 기준 |
| --- | --- |
| 데이터 | 테이블별 건수와 모든 행의 주요 키·값 일치 |
| 누락 | NULL과 숫자 0을 구분 |
| 조건 | upper_limit_raw와 단위 보존 |
| API | 상품·추천·프로필 상태 코드와 응답 계약 유지 |
| 쓰기 | 새 프로필 생성·조회, ID 충돌 없음 |
| 실패 | 비어 있지 않은 대상 거부, 부분 이관 없음 |

정렬·숫자 표현을 정규화한 비교 스크립트를 함께 검토합니다.

## 실패할 때 복구

API를 중지하고 PostgreSQL 오류 원인을 확인합니다.
SQLite로 돌아가야 하면 DATABASE_URL을 비우고
DATABASE_PATH를 검증된 백업으로 지정한 뒤 서버를 재시작합니다.

전환 후 새 데이터를 저장했다면 백업 복귀 전에 별도 보존해야 합니다.
자동 양방향 동기화는 이 실습 범위가 아닙니다.
`docker compose down`은 서버 중지용이며 `down -v`는 사용하지 않습니다.
