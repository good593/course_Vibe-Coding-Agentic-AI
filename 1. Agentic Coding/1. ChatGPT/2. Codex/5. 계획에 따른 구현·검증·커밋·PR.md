# 5. 계획에 따른 구현·검증·커밋·PR

## RAG 상담 기능을 검토 가능한 변경으로 전달하기

시작: 3장의 요구사항·4장의 구현 계획·프로젝트 규칙 준비

결과: 동작하는 상담 첫 버전 + 테스트·리뷰 근거가 있는 PR

---

## 이번 장의 작업 흐름

기준 main 정리 → feature 브랜치 → 프롬프트로 작은 단위 구현
→ 검증 Skill → diff 검토 → 커밋 Skill → PR Skill → CI·리뷰 반영

- 구현 내용은 계획과 현재 상황에 맞는 프롬프트로 요청합니다.
- 반복되는 검증·커밋·PR 절차는 제공 Skill로 수행합니다.
- 개발자는 범위·실행 결과·staged diff·리뷰 판단을 확인합니다.

---

## 3·4장의 문서를 입력으로 사용하기

| 자료 | 이번 장에서 사용할 내용 |
| --- | --- |
| 3장 요구사항 | 동작·정상/경계/실패 조건·완료 기준 |
| 4장 구현 계획 | 변경 파일·구현 순서·검증·커밋/PR 단위 |
| AGENTS.md | 프로젝트 공통 규칙과 보존 조건 |
| Skill | 문서를 읽고 반복 절차를 수행하는 방법 |

RAG의 세부 계약은 요구사항·계획·명세에서 읽습니다.
계획이 바뀌면 이유와 영향을 기록하고 다음 구현·검증에 반영합니다.

## [gh란?](https://cli.github.com/) 
- gh는 GitHub CLI의 실행 명령어입니다. 터미널에서 GitHub의 저장소, 이슈, Pull Request 등을 관리할 때 씁니다.

| 명령어 | 주로 하는 일 |
|---|---|
| `git` | 로컬 코드의 변경 기록, 브랜치, 커밋 관리 |
| `gh` | GitHub의 PR, 이슈, 저장소 관리 |

- gh 설치 
```powershell
# 설치 
winget install --id GitHub.cli
# 설치 확인 
gh --version
```

## 단계 2. 제공 Skill을 프로젝트에 준비

```powershell
New-Item -ItemType Directory -Path .agents/skills -Force
foreach ($skillName in @('verify-changes', 'commit-changes', 'create-pr')) {

```

같은 이름이 이미 있으면 본문을 비교하고 사용할 버전을 확인합니다.

## 키 없이 동작하는 CI 준비

chore/codex-setup에서 기존 workflow가 없는 경우만 실행합니다.

```powershell
# Git 루트의 workflow 폴더를 준비합니다.
New-Item -ItemType Directory -Path ../.github/workflows -Force
# 제공된 CI 예시를 실제 workflow 위치에 복사합니다.
Copy-Item -LiteralPath ../docs/templates/ci.yml -Destination ../.github/workflows/ci.yml
# 경로·명령을 읽고 확인한 파일만 커밋합니다.
git add -- ../.github/workflows/ci.yml
git diff --cached
git commit -m "ci: run locked Python tests and Ruff"
```

기존 CI가 있으면 복사하지 않고 계획대로 필요한 항목만 수정합니다.

## 단계 3. 준비 상태를 main에 반영

준비 브랜치에 미커밋 변경이 없는지 확인한 뒤 실행합니다.

```powershell
# 준비 작업을 기준 main에 fast-forward로 반영합니다.
git switch main
git merge --ff-only chore/codex-setup
# 학생의 origin/main에 준비 상태를 올립니다.
git push origin main
# 이후 비교할 기준 커밋을 기록합니다.
git rev-parse HEAD
```

fast-forward나 push가 거부되면 강사와 분기 상태를 확인합니다.
보호된 main은 준비 PR을 먼저 병합합니다. 강제 push하지 않습니다.

## 커밋 Skill: 후보 준비와 실행

먼저 파일별 목적·검증 근거·메시지를 검토합니다.

```text
$commit-changes
계획의 첫 번째 단위와 docs/reports/search-validation.md를 확인하고
커밋할 파일·목적·메시지를 제시해줘. 아직 stage/커밋하지 마.
```

제시된 파일·메시지를 확인한 뒤 실행을 요청합니다.

```text
$commit-changes
방금 검토한 첫 단위의 파일과 메시지로 stage·diff 점검·커밋해줘.
검증 이후 관련 코드가 바뀌었다면 필요한 재검증을 먼저 알려줘.
```

이후 단위도 같은 절차를 반복합니다. 커밋 해시와 남은 변경을 확인합니다.

## Skill이 수행하는 커밋 절차 이해하기

| 절차 | 확인할 내용 |
| --- | --- |
| 파일 선택·stage | 이번 단위의 코드·테스트·관련 기록인가? |
| git diff --cached | 커밋될 내용이 검증한 상태와 같은가? |
| git diff --cached --check | 패치·공백 오류가 없는가? |
| git commit | 내용에 맞는 메시지와 실제 해시가 있는가? |

다른 작업이 이미 stage되어 있으면 섞지 않고 범위를 확인합니다.
필수 검증 실패는 수정·재검증으로 이어갑니다.
검증 기록·PR 본문만 추가했다면 코드 검사 재실행 필요 여부를 판단합니다.

## 검증 결과를 현재 코드와 연결하기

검증 기록에는 HEAD, 검사 대상 파일 목록·SHA256을 남깁니다.
SHA256은 파일 내용이 바뀌었는지 비교하는 식별값입니다.

| 이후 변경 | 처리 |
| --- | --- |
| 코드·테스트·설정·lock·입력 자료 변경 | 영향받는 검증을 다시 수행 |
| 새 파일 추가·파일 삭제 | 검사 대상 목록도 다시 비교 |
| 코드가 같은 상태에서 커밋만 생성 | 내용이 같으면 기존 결과 사용 |
| 검증 기록·PR 본문만 변경 | 실행 영향 확인 후 기존 결과 연결 |

커밋·PR Skill은 과거 결과를 그대로 현재 검증으로 사용하지 않습니다.
별도 코드 리뷰에서는 요구사항 누락과 설계 문제도 확인합니다.

---

## 단계 10. API·화면 수동 확인

1장의 명령으로 FastAPI와 Streamlit을 실행합니다.

| 확인 | 기대 결과 |
| --- | --- |
| /health·상품 목록 | products=44·페이지 이동 유지 |
| 근거가 있는 질문 | 답변·문서명·출처·원문 위치 표시 |
| 근거가 없는 질문 | 부족 안내·빈 인용 |
| 공백 질문 | 입력 오류 안내 |
| 외부 API 장애 | 장애 안내, 성공 답변으로 숨기지 않음 |

합성 자료는 테스트에서 확인합니다. 실제 화면은 검수한 공식 자료를 씁니다.

---

## 단계 11. Groq 연결과 상담을 구분

.env에 실제 GROQ_API_KEY·GROQ_MODEL·LLM_PROVIDER=groq를 설정합니다.

```powershell
# 기존 모듈의 연결 점검입니다. RAG 전체 검증은 아닙니다.
uv run --locked python -m scripts.check_llm --live
```

그다음 구현한 상담 API나 별도 점검 명령으로 실제 질문을 보냅니다.
답변·인용·원문 일치·응답시간을 확인합니다.
모델·시각·자료·소요시간을 기록하고 질문 원문·키는 로그에 남기지 않습니다.

## 수동·실제 호출 결과를 검증 기록에 연결

관찰한 결과를 제공하고 자동 검사 결과와 구분해 기록합니다.

```text
$verify-changes
방금 확인한 API·화면·실제 Groq 결과를
docs/reports/rag-validation.md에 반영해줘.
내가 제공한 결과와 네가 직접 실행한 결과를 구분하고
완료 조건별 충족 여부와 미실행 항목을 갱신해줘.
검사 대상이 같으면 기존 자동 검사 결과를 연결해줘.
```

실제 관찰 결과를 함께 전달합니다. 실행하지 않은 항목은 이유를 적습니다.

## 실제 자료·계정이 준비되지 않았다면

| 항목 | 기록 방법 |
| --- | --- |
| 모의 테스트 성공 | 테스트 결과와 사용한 fixture |
| 공식 자료 미준비 | 준비할 문서·검수 담당·다음 확인 |
| 실제 Groq 미실행 | 이유와 재실행 조건 |
| PR·CI 완료 | 해당 코드 검증·전달의 실제 상태 |

코드 PR은 만들 수 있어도 실제 RAG 상담 검증은 미완료입니다.
전체 서비스 완료나 실제 상담 성공으로 표현하지 않습니다.

## 단계 12. 새 채팅에서 코드 리뷰

```text
main 대비 이번 RAG 변경을 리뷰해줘. 아직 코드를 수정하지 마.
커밋된 diff, staged/unstaged 변경, 새 파일을 모두 확인해줘.
요구사항·계획과 비교해 근거 없는 답변, 인용 검증 누락,
비밀값·상담 내용 저장, 실패를 성공으로 감추는 처리,
기존 API 회귀와 테스트 누락을 우선 확인해줘.
발견 사항마다 파일·위치·재현 조건·영향을 적어줘.
실행하지 못한 검증은 구분해서 보고해줘.
../docs/templates/change-review.md 형식으로
docs/reports/rag-review.md에 기록해줘. 발견 사항이 없으면 없다고 적어줘.
```

CLI 사용자는 지원되는 /review에서 기준 브랜치 main을 선택할 수 있습니다.
리뷰 결과는 전체 검증 기록과 별도로 남깁니다.

## 단계 13. 지적 사항 재현과 수정

```text
리뷰의 [검토할 항목]이 실제 문제인지 재현해줘.
재현되면 회귀 테스트와 수정을 반영해줘.
재현되지 않으면 판단 근거와 남은 불확실성을 설명해줘.
../docs/templates/change-review.md를 참고해
docs/reports/rag-review.md에 실제 결과를 기록해줘.
```

실제 지적 내용을 대괄호에 넣습니다. 모든 지적을 자동 수용하지 않습니다.
수정 후 verify-changes로 전체 기록의 필요한 검증을 갱신합니다.
결과와 diff 검토 후 commit-changes로 수정 커밋을 추가합니다.

## 단계 14. PR Skill로 본문 준비

```text
$create-pr
학생 저장소의 main ← feat/rag-chatbot PR 본문을 준비해줘.
요구사항·계획, docs/reports/rag-validation.md와
docs/reports/rag-review.md를 확인해줘.
../docs/templates/pr-body.md 형식으로 docs/pr/rag-chatbot.md를 작성해줘.
최신 코드의 검증 결과와 실제 Groq 미실행 여부를 반영해줘.
본문 준비만 하고 아직 push/PR 생성은 하지 마.
```

본문·제목·base/head·미실행 항목을 검토합니다.

## 전달 문서 커밋

```text
$commit-changes
검토한 docs/pr/rag-chatbot.md와 이번 검증·리뷰 기록 중
미커밋 전달 문서를 확인하고 문서 커밋을 만들어줘.
코드가 검증 이후 바뀌었다면 별도 변경으로 알려줘.
```

검증 보고서·PR 본문은 내용 식별값 수집에서 제외합니다.
실행에 영향을 주는 문서·설정 변경은 재검증 여부를 확인합니다.

## 단계 15. 기능 브랜치 push와 Draft PR

검토한 대상 저장소·본문·브랜치를 지정해 게시를 요청합니다.

```text
$create-pr
검토한 학생 저장소의 origin에 feat/rag-chatbot을 push하고
main을 base로 Draft PR을 만들어줘.
검토·커밋한 docs/pr/rag-chatbot.md와 제안 제목을 사용해줘.
기존 PR이 있으면 중복 생성하지 말고 그 PR을 갱신해줘.
실제 PR URL·base/head·head 커밋과 CI 상태·링크를 확인해줘.
```

Skill은 git push와 gh pr create --body-file로 전달합니다.
gh가 없으면 준비한 본문으로 웹에서 생성하고 실제 URL을 기록합니다.
PR 생성과 CI 성공은 구분합니다. 게시 결과가 불명확하면 먼저 조회합니다.

## 단계 16. CI 확인과 실패 대응

```text
$create-pr
현재 PR의 최신 head 커밋에 대한 CI 상태와 실행 링크를 확인해줘.
이번에는 상태 조회만 하고 실패가 있으면 로그와 원인을 요약해줘.
```

pending·실패·검사 없음은 성공으로 표시하지 않습니다.
실패한 job의 실제 로그를 확인하고 구현 프롬프트로 수정을 요청합니다.

```text
이 PR의 CI에서 [실제 오류 로그]가 발생했어.
로컬과 CI의 작업 폴더·자료 경로·Python·lock을 비교하고
원인을 조사해줘. 재현되면 수정하고 관련 검증을 실행해줘.
검사를 비활성화하거나 실패를 무시해서 통과시키지 마.
```

수정 → verify-changes → diff 검토 → commit-changes 순서로 진행합니다.
create-pr에 후속 push·본문 갱신·새 CI 확인을 요청합니다.
