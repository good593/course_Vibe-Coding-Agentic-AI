# 5. 계획에 따른 구현·검증·커밋·PR

## RAG 상담 기능을 검토 가능한 변경으로 전달하기

시작: 요구사항·구현 계획·프로젝트 규칙 준비

결과: 동작하는 상담 첫 버전 + 테스트·리뷰 근거가 있는 PR

---

## 이번 장의 작업 흐름

기준 main 정리 → feature 브랜치 → 작은 단위 구현
→ 테스트 → diff 리뷰 → 커밋 → PR → CI·리뷰 반영

- Codex는 조사·구현·검증·커밋·PR 작성에 사용합니다.
- 개발자는 범위·실행 결과·staged diff·리뷰 판단을 확인합니다.
- 기능 전체를 한 번에 구현하고 마지막에만 검증하지 않습니다.

---

## 단계 1. 저장소와 준비 변경 확인

project 터미널에서 학생 실습 저장소인지 확인합니다.

```powershell
# 현재 브랜치·Git 루트·원격 저장소를 확인합니다.
git status --short --branch
git rev-parse --show-toplevel
git remote -v
# GitHub CLI 인증과 대상 저장소를 확인합니다.
gh auth status
gh repo view --json nameWithOwner,url,defaultBranchRef
```

main에 시작 코드가 있고 chore/codex-setup에 준비 변경이 커밋되어야 합니다.
GitHub 준비는 [강사 진행 가이드](<docs/강사 진행 가이드.md>)를 참고합니다.

---

## 단계 2. 키 없이 동작하는 CI 준비

chore/codex-setup에서 기존 workflow가 없는 경우만 실행합니다.

```powershell
# Git 루트의 workflow 폴더를 준비합니다.
New-Item -ItemType Directory -Path ../.github/workflows -Force
# 제공된 CI 예시를 실제 workflow 위치에 복사합니다.
Copy-Item -LiteralPath ../docs/templates/ci.yml -Destination ../.github/workflows/ci.yml
# 경로·명령을 읽고 확인한 파일만 커밋합니다.
git add -- ../.github/workflows/ci.yml
git diff --cached
git commit -m "ci: run locked Python tests and Ruff"
```

기존 CI가 있으면 복사하지 않고 계획대로 필요한 항목만 수정합니다.

---

## CI에서 확인할 내용

| 확인 | 기준 |
| --- | --- |
| workflow 위치 | Git 루트의 .github/workflows/ci.yml |
| 실행 폴더 | project |
| 자료 경로 | docs·data까지 checkout |
| 환경 | Python 3.13·uv.lock의 의존성 |
| 검사 | pytest·ruff check·ruff format --check |
| 외부 호출 | Groq 키 없이 모의 테스트 |

workflow 파일이 있다는 사실과 GitHub 실행 성공을 구분합니다.

---

## 단계 3. 준비 상태를 main에 반영

준비 브랜치에 미커밋 변경이 없는지 확인한 뒤 실행합니다.

```powershell
# 준비 작업을 기준 main에 fast-forward로 반영합니다.
git switch main
git merge --ff-only chore/codex-setup
# 학생의 origin/main에 준비 상태를 올립니다.
git push origin main
# 이후 비교할 기준 커밋을 기록합니다.
git rev-parse HEAD
```

fast-forward나 push가 거부되면 강사와 분기 상태를 확인합니다.
보호된 main은 준비 PR을 먼저 병합합니다. 강제 push하지 않습니다.

## 단계 4. 기능 브랜치와 새 Codex 채팅

```powershell
# 준비된 main에서 기능 작업을 시작합니다.
git switch -c feat/rag-chatbot
```

```text
AGENTS.md, docs/requirements/rag-chatbot.md,
docs/plans/rag-chatbot.md를 읽고 현재 브랜치를 확인해줘.
다음 구현 단위와 검증 방법을 요약해줘.
계획과 다른 변경이 필요하면 이유와 영향부터 설명해줘.
이번 브랜치에서 구현·검증하되 커밋은 검토 후에 진행할게.
```

새 채팅이 준비 문서만으로 작업을 이어갈 수 있는지 확인합니다.

## 단계 5. 첫 구현 단위: 문서 검색

```text
계획의 첫 단위를 구현해줘. 문서 로딩·공식 검수 필터·검색을
backend의 계획한 모듈에 추가해줘.
최대 3개와 동점 정렬을 결정적으로 처리해줘.
../docs/fixtures/rag_test_corpus.json은 테스트에만 주입하고
실제 상담에서는 합성 자료를 거부해줘.
매칭·무매칭·정렬·필터·잘못된 레코드 테스트를 실행해줘.
기존 상품 코드·DB·CSV는 보존하고 아직 커밋하지 마.
```

작은 단위의 구현과 테스트가 함께 끝났는지 확인합니다.

---

## 단계 6. diff 확인과 첫 커밋

```text
이번 검색 변경의 파일별 목적과 검증 결과를 설명해줘.
신규 파일도 포함해 커밋 후보를 제시해줘.
계획과 무관한 변경이나 불필요한 의존성이 있는지 확인해줘.
```

```powershell
# 새 파일·추적 파일의 상태와 변경을 확인합니다.
git status --short
git diff
```

VS Code에서 검색 모듈과 관련 테스트만 stage합니다.
다음 슬라이드의 공통 커밋 절차로 검토하고 커밋합니다.

---

## 각 구현 단위의 공통 커밋 절차

stage한 파일이 이번 작업의 파일인지 읽고 실행합니다.

```powershell
# 커밋에 들어갈 파일과 내용을 확인합니다.
git diff --cached --stat
git diff --cached
# 공백·패치 형식 오류를 확인합니다.
git diff --cached --check
# 첫 검색 단위의 검증된 변경을 커밋합니다.
git commit -m "feat: retrieve verified reference passages"
```

두 번째·세 번째 단위는 실제 변경에 맞는 메시지로 바꿉니다.
Codex에게 커밋을 맡길 때는 확인한 파일·메시지를 명시합니다.

## 단계 7. 생성·인용 검증·API 구현

```text
계획의 두 번째 단위인 생성·인용 검증·POST /api/chat을 구현해줘.
실습 명세의 200/422/503과 status·citations 계약을 지켜줘.
선택 문단 ID를 검사하고 서버 레코드로 출처를 구성해줘.
무매칭은 생성기 미호출, API 장애·파싱·인용 오류는 실패로 처리해줘.
모의 생성기를 주입해 정상·부족·장애·잘못된 인용을 테스트해줘.
기존 TextGenerator의 고정 응답을 상담 완료로 보고하지 마.
관련·기존 테스트를 실행하고 결과를 보고해줘. 아직 커밋하지 마.
```

검증·staged diff 확인 후 두 번째 커밋을 만듭니다.

## 단계 8. 화면 연결과 실행 안내

```text
세 번째 단위인 Streamlit 상담 화면과 API 클라이언트를 구현해줘.
질문·답변·출처·근거 부족·장애 안내를 표시하고
기존 상품 조회·페이지 이동을 유지해줘.
상담 내용을 DB·파일·로그에 저장하지 마.
모의 API 화면 테스트와 전체 검증을 수행해줘.
추가 설정은 .env.example과 README에 설명하고 키는 넣지 마.
실제 Groq 상담을 별도로 점검하는 명령도 제공해줘.
```

검증·diff 확인 후 세 번째 커밋을 만듭니다.

## 단계 9. 전체 자동 검증

```powershell
# 기존·신규 테스트를 함께 실행합니다.
uv run --locked python -m pytest -q --basetemp=.pytest_cache/tmp
# 코드 규칙과 서식을 확인합니다.
uv run --locked ruff check .
uv run --locked ruff format --check .
# 기준 main 대비 커밋한 변경을 확인합니다.
git diff main...HEAD --stat
```

새 테스트 수는 학생 구현에 따라 달라집니다.
통과·실패·skip 수와 실행 환경을 기록합니다.

---

## 단계 10. API·화면 수동 확인

1장의 명령으로 FastAPI와 Streamlit을 실행합니다.

| 확인 | 기대 결과 |
| --- | --- |
| /health·상품 목록 | products=44·페이지 이동 유지 |
| 근거가 있는 질문 | 답변·문서명·출처·원문 위치 표시 |
| 근거가 없는 질문 | 부족 안내·빈 인용 |
| 공백 질문 | 입력 오류 안내 |
| 외부 API 장애 | 장애 안내, 성공 답변으로 숨기지 않음 |

합성 자료는 테스트에서 확인합니다. 실제 화면은 검수한 공식 자료를 씁니다.

## 단계 11. Groq 연결과 상담을 구분

.env에 실제 GROQ_API_KEY·GROQ_MODEL·LLM_PROVIDER=groq를 설정합니다.

```powershell
# 기존 모듈의 연결 점검입니다. RAG 전체 검증은 아닙니다.
uv run --locked python -m scripts.check_llm --live
```

그다음 구현한 상담 API나 별도 점검 명령으로 실제 질문을 보냅니다.
답변·인용·원문 일치·응답시간을 확인합니다.
모델·시각·자료·소요시간을 기록하고 질문 원문·키는 로그에 남기지 않습니다.

---

## 실제 자료·계정이 준비되지 않았다면

| 항목 | 기록 방법 |
| --- | --- |
| 모의 테스트 성공 | 테스트 결과와 사용한 fixture |
| 공식 자료 미준비 | 준비할 문서·검수 담당·다음 확인 |
| 실제 Groq 미실행 | 이유와 재실행 조건 |
| PR·CI 완료 | 해당 코드 검증·전달의 실제 상태 |

코드 PR은 만들 수 있어도 실제 RAG 상담 검증은 미완료입니다.
전체 서비스 완료나 실제 상담 성공으로 표현하지 않습니다.

## 단계 12. 새 채팅에서 코드 리뷰

```text
main 대비 이번 RAG 변경을 리뷰해줘. 아직 코드를 수정하지 마.
커밋된 diff, staged/unstaged 변경, 새 파일을 모두 확인해줘.
요구사항·계획과 비교해 근거 없는 답변, 인용 검증 누락,
비밀값·상담 내용 저장, 실패를 성공으로 감추는 처리,
기존 API 회귀와 테스트 누락을 우선 확인해줘.
발견 사항마다 파일·위치·재현 조건·영향을 적어줘.
실행하지 못한 검증은 구분해서 보고해줘.
```

CLI 사용자는 지원되는 /review에서 기준 브랜치 main을 선택할 수 있습니다.

## 단계 13. 지적 사항 재현과 수정

```text
리뷰의 [검토할 항목]이 실제 문제인지 재현해줘.
재현되면 회귀 테스트와 수정을 반영하고 영향받는 검증을 실행해줘.
재현되지 않으면 판단 근거와 남은 불확실성을 설명해줘.
../docs/templates/change-review.md를 참고해
docs/reports/rag-review.md에 실제 결과를 기록해줘.
```

실제 지적 내용을 대괄호에 넣습니다. 모든 지적을 자동 수용하지 않습니다.
수정·검증·diff 확인 후 필요한 수정 커밋을 추가합니다.

## 단계 14. PR 본문 작성

```text
main...HEAD와 이번 검증 기록을 확인하고
../docs/templates/pr-body.md 형식으로 docs/pr/rag-chatbot.md를 작성해줘.
사용자 문제와 변경 후 동작을 먼저 설명해줘.
실습ID, 주요 결정, 실제 테스트·Ruff·수동 확인 결과,
실제 Groq 성공 또는 미실행 이유를 포함해줘.
diff에 없는 기능이나 실행하지 않은 검증을 완료라고 쓰지 마.
아직 push/PR 생성은 하지 마.
```

본문과 기록을 검토하고 관련 문서도 커밋합니다.

## 단계 15. 기능 브랜치 push와 Draft PR

대상 저장소·main·feat/rag-chatbot을 다시 확인한 뒤 실행합니다.

```powershell
# 학생 저장소로 기능 브랜치를 올립니다.
git push -u origin feat/rag-chatbot
# 파일의 실제 줄바꿈을 유지한 PR 본문을 사용합니다.
gh pr create --base main --head feat/rag-chatbot --draft `
  --title "feat: add grounded RAG consultation" `
  --body-file docs/pr/rag-chatbot.md
# PR의 실제 URL을 확인합니다.
gh pr view --json url,baseRefName,headRefName
```

백틱 뒤에 주석·공백을 붙이지 않습니다. gh가 없으면 GitHub 웹에서 생성합니다.

## 단계 16. CI 확인과 실패 대응

```powershell
# 현재 PR의 검사 결과를 확인합니다.
gh pr checks
```

실패한 job의 로그를 열어 Codex에 제공합니다.

```text
이 PR의 CI에서 [실제 오류 로그]가 발생했어.
로컬과 CI의 작업 폴더·자료 경로·Python·lock을 비교하고
원인을 조사해줘. 재현되면 수정하고 관련 검증을 실행해줘.
검사를 비활성화하거나 실패를 무시해서 통과시키지 마.
```

수정 커밋을 push한 뒤 새 CI 실행을 확인합니다.

## 단계 17. 리뷰 요청과 후속 수정

CI와 본문을 확인한 뒤 Draft를 해제합니다.

```powershell
# 리뷰 가능한 상태로 변경합니다.
gh pr ready
# 리뷰 상태·본문·검사 링크를 웹에서 확인합니다.
gh pr view --web
```

강사·동료에게 리뷰를 요청합니다. GitHub Codex 리뷰가 설정된 저장소는
@codex review를 사용할 수 있습니다. 로컬 리뷰와 별도로 기록합니다.
지적을 재현·판단하고 수정 커밋·push·CI 재확인을 수행합니다.
