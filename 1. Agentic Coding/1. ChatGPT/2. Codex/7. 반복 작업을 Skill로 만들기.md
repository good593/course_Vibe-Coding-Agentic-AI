# 7. 반복 작업을 Skill로 만들기

## 검증 절차를 다시 설명하지 않기

시작: AGENTS.md, 리뷰 기준, 6장 스킬 형식 확인

결과: 변경 검증 스킬과 데이터 품질 점검 스킬

---

## 먼저 경험할 문제

기능 추가와 DB 전환 때마다 같은 요청을 반복했습니다.

요구사항 확인 → 변경 범위 확인 → 테스트 → 리뷰 → 결과 보고

- AGENTS.md: 프로젝트 전반에서 지킬 규칙
- Skill: 특정 작업을 수행하는 절차와 출력 형식
- 예약 작업: 검증된 절차를 실행할 시점

이번 장은 수동으로 스킬을 검증하는 데 집중합니다.

---

## 단계 1. 실제 반복 사례 선택

```text
1장의 추천 기능 검증과 5장의 DB 전환 검증 기록을 읽어줘.
공통 절차와 각 작업에서만 필요한 검증을 나눠줘.
healthy-day-review라는 변경 검증 스킬의 입력·출력·실행 조건을
제안해줘. 아직 스킬 파일을 생성하지 마.
```

처음부터 개발 전체를 처리하는 거대한 스킬을 만들지 않습니다.

---

## 단계 2. 스킬 생성 요청

Codex에서 `$`를 입력해 skill-creator를 선택할 수 있으면 사용합니다.

```text
$skill-creator
우리 프로젝트의 변경 검증을 healthy-day-review 스킬로 만들어줘.
저장 위치는 .agents/skills/healthy-day-review/SKILL.md야.
입력은 요구사항ID와 검토할 변경 범위이고,
출력은 변경 파일·검증 명령·결과·발견 사항·미실행 항목이야.
검증만 수행하고 코드를 자동 수정하거나 커밋하지 않게 해줘.
```

creator가 없다면 동일한 요구로 아래 형식의 파일을 직접 작성합니다.

---

## 단계 3. 메타데이터 확인

`SKILL.md`의 앞부분 예시:

```yaml
---
name: healthy-day-review
description: >-
  건강한하루의 기능 추가 또는 DB 변경 후 요구사항 충족,
  테스트와 diff를 검증한다. 코드 구현이나 수정 요청에는
  사용하지 않고 검증·리뷰·완료 점검 요청에 사용한다.
---
```

무슨 일을 하고 언제 사용하는지가 description에 있어야 합니다.

---

## 단계 4. 절차 확인

```markdown
1. AGENTS.md, README, docs/code_review.md를 읽는다.
2. 요구사항ID와 기준 변경 범위를 확인한다.
3. git status, staged/unstaged diff, 새 파일을 모두 확인한다.
4. 관련 테스트와 공통 검증을 실행한다.
5. DB 변경이면 보존·재실행·실패 복구 테스트도 확인한다.
6. 실제 PostgreSQL/Groq 연결과 모의 테스트를 구분한다.
7. 결과를 docs/reports/change-review.md에 기록한다.
8. 코드를 수정하거나 커밋하지 않는다. 실패를 성공으로 바꾸지 않는다.
```

보고서 자신은 코드 변경 리뷰 대상에서 제외합니다.

---

## 단계 5. 명시적으로 호출

새 채팅에서 `$`를 입력해 `healthy-day-review`를 선택합니다.

```text
$healthy-day-review
RF-1.1~1.3 구현을 검토해줘.
범위는 [1장 시작 커밋]부터 [1장 완료 커밋]까지야.
결과 보고서는 docs/reports/07-review-case1.md에 저장해줘.
```

대괄호는 자신의 실제 커밋 해시로 바꿉니다.
스킬이 안 보이면 경로·메타데이터를 확인하고 Codex를 재시작합니다.

---

## 단계 6. 두 번째 사례로 검증

```text
$healthy-day-review
이번에는 PostgreSQL 전환 변경을 검토해줘.
범위는 [전환 전 커밋]부터 [전환 후 커밋]까지야.
두 DB의 실제 검증 여부와 데이터 보존 근거를 확인해줘.
결과는 docs/reports/07-review-case2.md에 저장해줘.
```

두 보고서의 형식은 같고 작업별 검증 내용은 달라야 합니다.

---

## 단계 7. 실패도 정확히 보고하는지 확인

```text
현재 환경에서 실제 PostgreSQL 연결 검증을 실행할 수 없다면
미실행으로 표시해줘. SQLite나 모의 테스트 결과로 대체하지 마.
미실행 사유와 다음 확인 명령을 함께 적어줘.
```

실패를 만들기 위해 서비스 DB나 테스트를 고장 내지 않습니다.
별도 테스트 설정의 연결 누락 등으로 실패 보고를 확인합니다.

---

## 단계 8. 예약할 작업은 더 좁게 분리

다음 장에서는 **CSV 데이터 품질 점검**만 예약합니다.
제공된 점검 스크립트를 먼저 직접 실행합니다.

```powershell
uv run --locked python -m scripts.data_quality_report
```

`docs/reports/data-quality.md`에서 파일별 행 수·빈 값·해시를 확인합니다.
이 스크립트는 CSV를 읽고 보고서만 생성합니다.
DB나 원본 CSV를 수정하지 않습니다.

---

## 단계 9. 데이터 점검 스킬 생성

```text
healthy-day-data-audit 스킬을 .agents/skills 아래에 만들어줘.
명시적 데이터 품질 점검 요청에만 사용하도록 설명해줘.
작업 폴더와 ../data의 존재를 확인한 뒤
uv run --locked python -m scripts.data_quality_report를 실행해줘.
종료 코드와 docs/reports/data-quality.md를 읽고 결과를 요약해줘.
원본·DB·설정은 수정하지 않고 누락값을 임의 보정하지 않아야 해.
실행 실패나 파일 부재를 정상으로 보고하지 않게 해줘.
```

---

## 단계 10. 같은 입력으로 반복 실행

```text
$healthy-day-data-audit
현재 CSV 3개의 품질을 점검하고 보고서를 읽어 요약해줘.
```

두 번 실행하고 실행 시각을 제외한 건수·누락·해시가 같은지 봅니다.
최소 2~3개 사례에서 스킬의 적용 범위와 실패 처리를 검증합니다.

보고서의 ‘구조 점검 완료’는 데이터의 의학적 정확성을 뜻하지 않습니다.
