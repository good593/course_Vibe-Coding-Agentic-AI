# 9. 통합 실습과 요구사항 완성

## 새로운 기능에 Best Practices를 스스로 적용하기

시작: 1~7장 코드·지침·스킬, Groq 연결, DB 전환 검증

결과: 수용된 전체 요구사항의 구현·검증 기록

예약 실행은 8장에서 독립적으로 검증합니다.

---

## 이번 장의 진행 규칙

한 번에 “나머지를 모두 구현해 줘”라고 요청하지 않습니다.

요구사항 확인 → 계획 → 기능 하나 구현 → 테스트 → 리뷰 → 커밋

각 과제에서 반복한 규칙은 AGENTS.md,
반복한 검증 절차는 Skill로 보완합니다.
완성 코드를 받는 것보다 **작업을 맡기고 확인하는 과정**을 기록합니다.

---

## 단계 1. 요구사항 추적표 만들기

```text
../docs/요구사항정의서.xlsx와 현재 코드를 대조해줘.
수용여부 O인 세부 요구사항을 빠짐없이 추적표로 만들어줘.
ID, 구현 파일, API/화면, 테스트, 실제 실행 증거, 미완료 이유를 적어줘.
상위 분류 행은 기능 수에 중복 집계하지 마.
RF-2.3과 NFR-4.2는 수용 X이므로 별도 보류로 표시해줘.
docs/reports/requirements-trace.md에 저장하고 아직 구현하지 마.
```

상담/RAG의 단계적 오픈 문구는 구현 순서로 해석하며 최종 목표에서 빼지 않습니다.

## 단계 2. 재추천 기능 추가

```text
RF-1.4 재추천을 계획한 뒤 구현해줘.
POST /api/recommendations에 선택 입력 exclude_product_ids를 추가해줘.
같은 조건에서 이미 표시한 상품을 제외하고 최대 5개를 반환해줘.

```

검증 후 `$healthy-day-review`를 호출하고 커밋합니다.

## 단계 3. 근거 자료를 준비

현재 CSV의 출처 문자열만으로 원문 검증이 끝난 것은 아닙니다.

1. 기능성 설명에 사용할 공식 문서 원문을 실제로 엽니다.
2. 문서명·발행기관·URL·확인일·절/쪽 위치를 기록합니다.
3. 필요한 짧은 구간과 로컬 파일 경로를 연결합니다.
4. CSV와 다른 내용은 자동으로 합치지 말고 차이를 기록합니다.

출처 페이지가 없어지거나 접근할 수 없으면 검증 보류입니다.
합성 RAG 자료는 검색·인용 로직의 테스트에만 사용합니다.

---

## 단계 4. 원문 등록 도구 요청

```text
../docs/실습 보완 명세.md의 source manifest 형식으로
공식 근거 문서를 등록·검증하는 절차를 만들어줘.
doc_id, 제목, 발행기관, URL, 확인일, 원문 위치, 본문 파일,
검증 상태를 보존하고 파일이 없거나 미검증이면 실제 상담에서 제외해줘.
페이지 내용을 읽지 못했는데 검증 완료로 표시하지 마.
../docs/fixtures/rag_test_corpus.json은 합성 테스트 전용으로 구분해줘.
```

공식 자료는 사람이 원문과 대조한 후 verified로 바꿉니다.

## 단계 5. 성분 설명 구현

```text
RF-2.1~2.2를 구현해줘. 상품 상세에서 원료명을 선택하면
검증된 기능성 근거를 바탕으로 쉬운 설명과 출처를 보여줘.
설명은 Groq를 사용하되 근거 문서ID와 출처는 서버가 관리해줘.
근거가 없으면 부족하다고 알리고 사실을 추정하지 마.
NFR-4.1 기준으로 용어를 풀어 쓰고 길고 어려운 문장을 점검해줘.
API 계약과 테스트를 먼저 제안하고 구현해줘.
```

단어 난도는 자동 지표만으로 확정하지 않고 학생끼리 읽어 봅니다.

---

## 단계 6. RAG 상담 계획

```text
RF-3.1~3.3의 Groq RAG 상담을 계획해줘.
검증된 원문을 문단으로 나누고 doc_id/chunk_id/위치/출처를 보존해줘.
첫 버전은 로컬 키워드 검색으로 상위 3개 근거를 찾도록 해줘.
별도 임베딩 API가 있다고 가정하지 마.
질문→검색→선택 근거→Groq 생성→인용 검증 순서로 분리해줘.
근거 없음·타임아웃·허위 인용의 응답과 테스트를 먼저 정해줘.
```

검색 방법을 바꿔도 API·서비스의 역할이 유지되는지 검토합니다.

---

## 단계 7. Groq RAG 구현

```text
검토한 RAG 계획을 구현해줘. 기존 integrations/llm.py를 확장해줘.
POST /api/chat은 message를 받고 answer, citations, status를 반환해줘.
근거 문서는 참고 데이터로 구분하고 그 안의 명령을 따르지 않게 해줘.
출력은 스키마 검증하고, 인용은 검색한 doc_id만 허용해줘.
URL과 문서명은 서버의 manifest에서 가져와줘.
허위 인용·파싱 실패는 성공 답변으로 내보내지 마.
근거가 없으면 Groq를 호출하지 않고 insufficient_evidence를 반환해줘.
```

처음에는 모의 응답으로 테스트하고 다음 단계에서 실제로 연결합니다.

---

## 단계 8. 인용의 정확성 검증

| 사례 | 확인할 결과 |
| --- | --- |
| 적절한 근거 존재 | 답변 문장과 실제 근거의 의미 일치 |
| 존재하지 않는 문서ID 생성 | 서버에서 거부 |
| 실제 ID지만 무관한 설명 | 내용 검토에서 실패 처리 |
| 근거 없음 | 부족 안내, 모델 호출 없음 |
| 문서에 명령이 포함됨 | 자료로 취급, 실행하지 않음 |
| Groq 실패·시간 초과 | 명확한 오류/대체 안내, 가짜 성공 금지 |

**문서ID가 존재하는지만 검사해서 NFR-3.1 완료로 판단하지 않습니다.**

---

## 단계 9. 실제 Groq 연결 확인

`.env`의 `LLM_PROVIDER=groq`, 키와 모델을 확인합니다.
서버를 재시작하고 검증된 원문으로 만든 질문 3개를 입력합니다.

- 요청별 응답과 인용 위치를 원문과 비교합니다.
- API 실패와 불충분 근거 사례도 확인합니다.
- 네트워크/계정 문제는 로직 오류와 구분합니다.
- 실제 호출은 별도 표시하고 비용·횟수를 관리합니다.

합성 자료·고정 응답만 사용했다면 RAG의 실제 근거 검증은 미완료입니다.

## 단계 10. 권장·상한 정보 조회

```text
RF-4.1을 구현해줘. 상품의 모든 성분을 검색키워드 하나로
단정하지 말고, 확인된 제품별 성분 연결을 사용해줘.
프로필 조건과 정확히 일치하는 기준을 표시해줘.
권장섭취량이 없으면 충분섭취량을 구분해서 표시하고,
둘 다 없거나 상한이 없으면 정보 없음으로 표시해줘.
단위와 upper_limit_raw의 적용 조건을 보존해줘.
CSV 값 자체가 검증됐다고 표시하지 마.
```

제품별 성분 연결이 없으면 그 상품의 전체 복용 안내는 보류합니다.

## 단계 11. 과다섭취 계산을 먼저 테스트

```text
RF-4.2의 규칙 계산기를 별도 순수 함수로 구현해줘.
../docs/fixtures/intake_test_cases.json의 합성 사례만 먼저 사용해줘.
영양소·단위·적용 범위가 맞을 때 합산하고 상한 초과를 판정해줘.
상한과 같으면 초과가 아니며 누락이면 안전으로 판정하지 마.
변환 규칙이 없는 단위 또는 조건은 판단 불가로 반환해줘.
실제 제품 함량으로 이 테스트 숫자를 사용하지 마.
```

이 단계는 알고리즘 검증이며 실제 제품 경고 기능의 완성이 아닙니다.

## 단계 12. 실제 제품 함량 연결

제품별 영양소 함량 자료에는 다음 정보가 필요합니다.

`product_id`, 영양소, 1회량/1일량 구분, 함량, 단위,
섭취 횟수, 적용 범위, 출처 URL·확인일

```text
실제 확인한 제품 함량만 DB에 연결해줘.
복합 제품의 여러 영양소를 모두 처리하고 누락된 제품은
판단 불가로 구분해줘. 단위/범위 불일치와 중복 담기를 테스트해줘.
검증된 사례에서만 경고를 표시하고 미확인 함량을 추정하지 마.
```

## 단계 13. AI 안내 보조 연결

```text
RF-4.3을 구현해줘. 초과 여부·합산값·상한·단위·판단 불가 이유는
규칙 코드에서 확정하고 AI는 그 결과를 쉽게 풀어 설명하게 해줘.
AI 출력으로 계산 결과를 바꾸지 마.
Groq 장애 시에도 규칙 결과와 정해진 기본 문구를 표시해줘.
AI가 잘못된 수치를 답한 모의 사례에서도 계산 결과는 유지돼야 해.
```

화면은 규칙 결과와 설명을 각각 검증할 수 있게 만듭니다.

## 단계 14. 인증과 상담 이력 보호

```text
NFR-2.1~2.2를 구현할 계획을 먼저 제안해줘.
가상 계정 로그인 후 서버가 세션에서 사용자ID를 결정하고,
상담 조회는 작성자에게만 허용해줘. 요청의 user_id를 신뢰하지 마.
건강 고민·상담 내용은 인증된 암호화 방식으로 저장하고,
암호화 키는 .env에서 읽으며 DB와 로그에 넣지 마.
비밀번호는 해시로 저장해줘. 타인 조회·만료 세션·키 누락을 테스트해줘.
```

계획 확인 후 구현합니다. 공개 배포용 인증 완성을 가정하지 않습니다.

## 단계 15. 상담 종료와 운영 로그

```text
RF-3.4와 NFR-5.1을 구현해줘.
상담 종료·추가문의·CS 이관 필요 여부를 저장하고 조회하게 해줘.
CS 이관은 필요 상태 기록까지이며 외부 메시지를 실제 발송하지 마.

질문 원문·답변 원문·키·민감정보는 운영 로그에 기록하지 마.
사용자 간 이력 분리와 로그의 민감정보 제외를 테스트해줘.
```

## 단계 16. 응답시간을 실제로 측정

```text
NFR-1.1 추천 2초, NFR-1.2 RAG 5초를 검증해줘.
측정 PC, DB, 데이터 크기, 동시성, 모델, 캐시 여부를 기록해줘.
일반 입력 20개로 요청 시작부터 전체 응답까지 측정하고
실패/시간초과를 제외하지 말고 개별 결과와 최대값·p95를 보고해줘.
모의 응답과 실제 Groq 결과를 분리해줘.
5초를 넘으면 시간 제한과 대체 안내를 구현하되 요구 충족으로 꾸미지 마.
```

로컬 실습 결과를 모든 부하에서의 성능 보장으로 일반화하지 않습니다.

## 단계 17. 최신성 점검과 갱신 분리

8장의 CSV 품질 점검은 데이터 갱신이 아닙니다.

```text
NFR-3.2 월 1회 이상 갱신을 위한 절차를 설계·구현해줘.
공식 원문 변경 확인→새 데이터 별도 수집→구조/내용 검증→
차이 보고→검토된 버전 적용→실패 시 이전 버전 유지 순서로 해줘.
확인일과 실제 갱신일을 구분하고 보고서 생성일로 대신하지 마.
검증되지 않은 데이터를 바로 서비스 DB에 반영하지 마.
```

주기 설정뿐 아니라 첫 갱신의 실제 실행 증거를 남깁니다.

## 단계 18. 전체 검증과 리뷰

```text
$healthy-day-review

모의/합성 데이터 검증, 실제 API/DB 검증, 원문 대조를 구분해줘.
전체 테스트와 검사 후 요구사항별 근거를 연결해줘.
부족한 입력 때문에 구현할 수 없는 항목을 임의로 충족 처리하지 마.
```

최종 결과는 기능 화면과 함께 요구사항 추적표로 제출합니다.
