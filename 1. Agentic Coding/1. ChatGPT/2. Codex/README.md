# Codex Best Practices 실습 강의

## 강의 목표

건강한하루 서비스를 확장하며 **Codex에게 맥락을 제공하고, 계획과 규칙을 만들고, 결과를 검증하는 방법**을 배웁니다. 웹서비스는 학습을 위한 공통 사례입니다. 학생별 생성 코드가 같아야 하는 것은 아니지만 API 계약과 완료 기준은 같아야 합니다.

학생은 Python·VS Code·Git/GitHub·터미널을 사용할 수 있다고 가정합니다. 주 환경은 VS Code Codex 확장, 구현은 Python 3.13·uv·Streamlit·FastAPI·sqlite3입니다. 이후 PostgreSQL과 Groq를 사용합니다.

## 공통 진행 방법

각 장은 시작 상태 → 짧은 탐색 → 불명확한 부분 확인 → 구체적인 요청 → 실행·검증 → 회고 순서입니다. 첫 요청이 잘 나와도 실패를 연출하지 않습니다. 어떤 조건을 추측했는지와 검증 가능한 근거가 남았는지 비교합니다.

1. 0장을 먼저 실행합니다. 이후 모든 명령의 기본 위치는 `project`입니다.
2. 코딩 프롬프트는 VS Code의 Codex 입력창에, `powershell` 명령은 터미널에 입력합니다.
3. 매 장에서 새로 만들도록 요청한 파일은 시작 코드에 아직 없습니다. 구현 완료 후 해당 명령을 실행합니다.
4. 모델 답변이 아닌 테스트 출력·API 응답·DB 비교·diff로 완료를 판단합니다.
5. 테스트가 통과한 코드를 커밋하고, 증거를 `project/docs/lab-notes/`에 기록합니다.

## 학생별 작업 공간과 복구

강의 저장소를 직접 수정하지 않으려면 이 폴더 전체(`docs`, `data`, `project` 포함)를 학생별 실습 폴더에 복사합니다. 복사한 폴더의 최상위에서 `git rev-parse --show-toplevel`로 현재 Git 루트를 확인합니다. 저장소가 없을 때만 `git init`을 실행합니다. 강의 저장소 안에 중첩 Git 저장소를 만들지 않습니다.

각 장 종료 시 `git status --short`로 변경을 확인하고, VS Code Source Control에서 이번 장의 파일만 선택해 커밋합니다. `.env`, DB 파일, 가상환경은 커밋하지 않습니다. 커밋 메시지는 `lab-01: recommendations`처럼 장 번호를 포함하고 해시를 기록합니다.

복구가 필요하면 현재 변경을 먼저 별도 커밋하거나 복사해 보관합니다. 강사가 확인한 이전 커밋에서 새 복구 브랜치를 만듭니다. 코드를 되돌려도 DB가 복구되지는 않으므로 DB 백업도 별도로 사용합니다. 무조건 `git reset --hard`하거나 DB를 삭제하지 않습니다.

현재 배포물에는 **검증된 0장 시작 코드**가 있습니다. 1~9장은 학생이 Codex로 구현하는 실습서이며 장별 완성 코드나 실행 완료 스크린샷을 제공한 것으로 표시하지 않습니다. 강사는 실제 수업 전 리허설에서 확인한 커밋을 반별 공통 재시작 지점으로 배포합니다.

## 강사 사전 확인

- [실습 보완 명세](<docs/실습 보완 명세.md>)의 수업용 결정과 원문 요구사항을 함께 확인합니다.
- 5장: Docker Desktop 또는 접속 가능한 실습용 PostgreSQL이 필요합니다.
- 6장: 외부 MCP 주소에 대한 네트워크 접근과 Codex 연결 권한을 확인합니다.
- 8장: 데스크톱 앱의 로컬 프로젝트·예약 작업 사용 가능 여부를 확인합니다. VS Code만으로 예약 생성까지 완료했다고 판단하지 않습니다.
- 9장: Groq 키·모델, 공식 원문 자료, 제품 함량 데이터의 준비 상태를 확인합니다. 없는 자료는 추정해서 채우지 않습니다.
- 실제 서비스 데이터가 부족한 경고 계산은 [합성 테스트 자료](<docs/fixtures/README.md>)로 알고리즘을 먼저 검증합니다.
- 계정·네트워크 의존 작업을 실행하지 못하면 `미실행`으로 기록합니다. 모의 테스트 통과와 실제 연결 성공을 구분합니다.

## 자료 검증 범위
