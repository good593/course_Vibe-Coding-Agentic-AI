# Codex 제품 지도

웹개발 작업을 어디에서, 어떤 권한으로 실행할 것인가

---

## 오늘의 목표

- Codex의 다섯 실행 표면을 구분한다.
- 작업 성격에 맞는 실행 표면과 환경을 선택한다.
- Codex에게 맡길 일과 사람이 결정할 일을 나눈다.
- 이후 강의에서 다룰 기능들의 연결 관계를 설명한다.

---

## Codex는 코드 생성기가 아니다

Codex의 기본 루프는 다음과 같다.

1. 저장소와 지침을 읽는다.
2. 변경 계획을 세운다.
3. 파일을 수정하고 명령을 실행한다.
4. 테스트와 diff로 결과를 검증한다.
5. 증거와 남은 위험을 보고한다.

핵심은 코드의 양이 아니라 **검증 가능한 작업 완료**다.

---

## 다섯 실행 표면

| 표면 | 잘 맞는 작업 | 강점 |
|---|---|---|
| Desktop app | 여러 프로젝트와 장기 작업 조정 | 프로젝트, Chat, Worktree, 통합 터미널 |
| CLI | 터미널 중심 로컬 개발 | 명령 조합, 세션 재개, 자동화 연결 |
| IDE extension | 코드 옆에서 짧은 수정 | 열린 파일·선택 영역 컨텍스트, diff |
| Codex Cloud | 격리된 장기·병렬 작업 | 호스팅 환경, 백그라운드 실행 |
| Remote | 다른 기기의 로컬 Codex 제어 | 이동 중 지시·승인·검토 |

---

## 실행 표면과 실행 환경은 다르다

- 실행 표면: 사람이 Codex와 대화하는 인터페이스
- 실행 환경: 코드와 명령이 실제로 실행되는 위치

예시:

- Desktop app에서 Local 실행
- Desktop app에서 Worktree 실행
- IDE extension에서 Cloud로 위임
- 모바일 Remote에서 연결된 PC의 Worktree 제어

항상 “어디에서 대화하는가?”와 “어디에서 실행되는가?”를 따로 확인한다.

---

## 작업 배치 기준

| 질문 | 선택 힌트 |
|---|---|
| 현재 편집 중인 코드가 핵심인가? | IDE |
| 로컬 명령과 도구를 계속 사용해야 하는가? | CLI 또는 Desktop Local |
| 현재 작업과 충돌 없이 병렬로 진행해야 하는가? | Worktree |
| 긴 작업을 격리해 맡겨야 하는가? | Cloud |
| 여러 저장소와 Chat을 한곳에서 조정하는가? | Desktop app |

---

## 사람이 계속 맡아야 하는 결정

- 요구사항과 우선순위 확정
- 운영 데이터와 비밀정보 사용 승인
- 파괴적 명령, 외부 전송, 배포 승인
- 테스트가 충분한지에 대한 최종 판단
- 제품·보안·법적 위험 수용 여부

Codex의 결과는 제안과 증거다. 책임의 이전이 아니다.

---

## 강사 시연

같은 요청을 세 표면에 입력해 차이를 관찰한다.

> 예약 목록에서 마감된 클래스의 버튼을 비활성화하고 테스트해줘. 먼저 관련 파일을 찾고 계획만 보여줘.

관찰 항목:

- 자동으로 확보한 컨텍스트
- 파일·명령 접근 범위
- 계획과 승인 흐름
- 결과를 검토하는 화면

---

## 실습: 작업 라우팅 카드

다음 작업을 적합한 표면과 환경에 배치한다.

1. 현재 열린 컴포넌트의 변수명 변경
2. 프런트·백 저장소를 함께 탐색
3. 30분 이상 걸리는 전체 테스트와 수정
4. 두 기능을 서로 충돌 없이 동시에 구현
5. 출퇴근 중 실행 상태 확인과 승인

각 선택에 “왜 이 표면인가?”를 한 문장으로 기록한다.

---

## 제출물

| 작업 | 실행 표면 | 실행 환경 | 권한 | 완료 증거 |
|---|---|---|---|---|
| 예: 버튼 수정 | IDE | Local | workspace-write | diff, UI 캡처, 테스트 |

완료 기준:

- 다섯 작업이 모두 배치되어 있다.
- 실행 표면과 환경을 혼동하지 않았다.
- 최소 권한과 검증 방법이 적혀 있다.
