# 프런트엔드 에이전트 루프

이미지·브라우저·터미널을 연결해 UI를 검증하기

---

## 오늘의 목표

- 화면 요구사항을 상태와 상호작용으로 분해한다.
- 이미지와 저장소 코드를 함께 컨텍스트로 사용한다.
- 기존 디자인 시스템을 탐색해 재사용한다.
- 브라우저와 테스트로 시각·접근성·동작을 검증한다.

---

## UI 구현 루프

1. 요구 화면과 상태를 관찰한다.
2. 기존 컴포넌트·토큰·라우팅을 탐색한다.
3. 계획과 변경 범위를 검토한다.
4. 최소 단위로 구현한다.
5. 브라우저에서 동작과 화면을 확인한다.
6. 테스트·스크린샷·diff로 증거를 남긴다.

---

## 이미지 입력의 역할

이미지는 다음을 전달하기 좋다.

- 레이아웃과 시각적 계층
- 오류·빈 상태의 실제 증상
- 반응형 화면 차이
- 기대 디자인과 현재 구현의 차이

이미지만으로는 동작·데이터·접근성 요구를 확정할 수 없다. 텍스트 요구사항을 함께 준다.

---

## 구현 전 저장소 탐색

Codex에게 먼저 찾도록 한다.

- 유사 화면과 재사용 가능한 컴포넌트
- 색상·간격·타이포그래피 토큰
- 데이터 fetching과 오류 처리 방식
- 테스트 도구와 selector 관례
- 반응형 breakpoint

새 컴포넌트를 만들기 전에 기존 패턴의 근거를 제시하게 한다.

---

## 상태 매트릭스

| 상태 | 확인할 UI | 확인할 동작 |
|---|---|---|
| 정상 | 예약 가능 정보 | 클릭·제출 |
| 로딩 | 진행 표시 | 중복 제출 방지 |
| 빈 상태 | 안내와 다음 행동 | 탐색 경로 제공 |
| 오류 | 이해 가능한 메시지 | 재시도·복구 |
| 권한 없음 | 접근 제한 안내 | 안전한 이동 |
| 마감 | 비활성화 표현 | 서버 검증과 일치 |

---

## 프롬프트 예시

```text
첨부한 화면을 참고해 예약 카드의 마감 상태를 구현해줘.
먼저 기존 Card·Button·token 사용 위치를 찾아 재사용 계획을 보여줘.

완료 기준:
- 360px와 1280px에서 레이아웃 확인
- 키보드 focus와 접근 가능한 이름 유지
- 마감 상태에서는 제출 불가
- 관련 컴포넌트 테스트 통과
```

---

## 브라우저 검증

- 실제 개발 서버 URL과 route 확인
- viewport별 레이아웃 비교
- 클릭·키보드·폼 제출 테스트
- 콘솔 오류와 네트워크 실패 확인
- 결과 스크린샷 저장

스크린샷이 예쁘다고 기능이 맞는 것은 아니다. DOM·네트워크·테스트 증거를 함께 본다.

---

## 접근성 빠른 점검

- 키보드만으로 주요 흐름을 완료할 수 있는가?
- focus가 보이는가?
- input과 label이 연결되어 있는가?
- 오류가 색상만으로 전달되지 않는가?
- 비활성화와 로딩 상태가 보조기술에 전달되는가?

자동 검사 통과는 수동 사용성 확인을 대체하지 않는다.

---

## 강사 시연

예약 카드의 정상·마감·로딩 상태를 구현한다.

- 이미지 요구 분석
- 기존 컴포넌트 탐색
- Plan 검토
- 구현과 테스트
- 브라우저 상호작용
- viewport별 스크린샷 비교

---

## 실습

`예약 폼`에 다음을 구현한다.

- 정상·로딩·서버 오류 상태
- 모바일·데스크톱 레이아웃
- 키보드 focus와 오류 안내
- 중복 제출 방지

필수 제출:

- 상태 매트릭스
- 변경 파일과 재사용 근거
- 두 viewport 스크린샷
- 테스트와 콘솔 결과
