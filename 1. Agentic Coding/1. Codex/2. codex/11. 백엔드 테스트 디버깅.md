# 백엔드·테스트·디버깅

재현 → 가설 → 최소 수정 → 회귀 검증

---

## 오늘의 목표

- API 요청에서 DB까지 실행 흐름을 추적한다.
- 실패를 최소 재현하고 근거 기반 가설을 세운다.
- 관련 테스트를 먼저 선택하고 실행한다.
- 수정 후 회귀와 미검증 범위를 보고한다.

---

## 디버깅 루프

1. 기대 결과와 실제 결과를 분리한다.
2. 최소 재현 절차를 만든다.
3. 로그·스택·코드로 경계를 좁힌다.
4. 원인 가설을 우선순위화한다.
5. 최소 범위로 수정한다.
6. 재현 테스트와 인접 회귀 테스트를 실행한다.

원인을 확정하기 전에 코드를 여러 곳 바꾸지 않는다.

---

## 흐름 추적

예약 생성 요청 예:

```text
route → middleware → validation → service
      → repository → database → response mapping
```

각 단계에서 확인할 것:

- 입력과 출력 타입
- 인증과 인가
- 오류 변환
- transaction 경계
- 재시도와 idempotency

---

## 재현 요청 예시

```text
중복 예약 요청이 500을 반환한다.
아직 수정하지 말고 다음을 수행해줘.

1. 관련 실행 경로를 파일과 심볼 기준으로 추적
2. 최소 재현 테스트 작성 또는 기존 테스트 식별
3. 가능한 원인과 반증 방법 제시
4. 가장 작은 수정 계획 제안
```

---

## 테스트 선택

| 테스트 | 목적 | 실행 시점 |
|---|---|---|
| 단위 | 함수·클래스 규칙 | 수정 중 빠른 피드백 |
| 통합 | 모듈·DB·API 경계 | 계약과 데이터 흐름 확인 |
| E2E | 사용자 수직 흐름 | 핵심 시나리오 최종 확인 |
| 정적 검사 | 타입·lint·format | 코드 품질과 일관성 |

전체 테스트가 비싸다면 가까운 테스트부터 넓혀 간다.

---

## 로그를 읽는 법

- 첫 원인과 연쇄 오류를 구분한다.
- timestamp와 request ID를 맞춘다.
- 전체 스택에서 애플리케이션 경계를 찾는다.
- 비밀값·개인정보를 프롬프트에 넣기 전 마스킹한다.
- 일부 로그만 제공했다면 추론임을 표시하게 한다.

---

## 최소 수정

좋은 수정:

- 재현된 원인만 해결한다.
- 공개 계약 변경을 최소화한다.
- 오류를 삼키지 않는다.
- 임시 우회 대신 불변식을 복구한다.
- 실패했던 경로를 테스트로 고정한다.

리팩터링 욕심은 별도 작업으로 분리한다.

---

## 강사 시연

버그: 정원이 1명 남은 클래스에 동시 예약이 들어오면 초과 예약된다.

- 실행 경로 탐색
- 동시성 재현 테스트
- transaction·constraint 확인
- 최소 수정
- 단위·통합 테스트와 로그 검토

---

## 실습

다음 버그 중 하나를 해결한다.

- 중복 예약이 500을 반환
- 취소된 예약이 인원수에 포함
- 시간대 변환으로 마감 시각이 어긋남

필수 기록:

- 재현 절차와 실제 출력
- 가설 목록과 제거 근거
- 변경 파일과 이유
- 테스트 명령·결과·종료 코드
- 확인하지 못한 운영 조건
