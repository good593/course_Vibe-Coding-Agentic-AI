# Code Review와 협업

변경을 찾는 리뷰에서 위험을 설명하는 리뷰로

---

## 오늘의 목표

- 리뷰 기준 범위를 올바르게 선택한다.
- Codex 리뷰 결과를 근거와 심각도로 평가한다.
- `AGENTS.md` 리뷰 규칙을 활용한다.
- PR과 외부 협업 도구에 검증 결과를 전달한다.

---

## 무엇을 리뷰할 것인가

- 미커밋 변경: 현재 작업 중인 diff
- 특정 commit: 독립 변경 단위
- 기준 branch와 비교: PR 전체 범위

리뷰 시작 전 확인:

- 기준 branch가 맞는가?
- 생성 파일과 lockfile이 포함되는가?
- 사용자 로컬 변경이 섞였는가?

---

## 리뷰 요청 예시

```text
현재 branch를 main과 비교해 리뷰해줘.
정확성·인증/인가·데이터 손실·회귀를 우선한다.
스타일 의견은 기능 위험이 있을 때만 제시한다.

각 finding에 포함:
- 심각도
- 파일과 줄
- 실패 시나리오
- 코드 근거
- 최소 수정 방향
```

---

## 좋은 Finding

좋은 리뷰 지적은 다음을 연결한다.

```text
코드 위치 → 현재 동작 → 실패 조건 → 사용자 영향 → 수정 방향
```

피해야 할 것:

- 근거 없는 가능성 나열
- 취향 수준의 스타일 지적
- 변경 범위 밖의 대규모 재설계
- 테스트 없이 “문제없음” 결론

---

## 심각도 판단

| 수준 | 예시 |
|---|---|
| 치명적 | 인증 우회, 데이터 손실, 비밀 노출 |
| 높음 | 핵심 흐름 중단, 잘못된 결제·권한 처리 |
| 중간 | 특정 조건의 기능 오류, 의미 있는 회귀 |
| 낮음 | 제한적 품질 문제, 유지보수 위험 |

발생 가능성과 영향도를 함께 본다.

---

## AGENTS.md와 리뷰

`## Code Review Rules`에 저장소 특화 기준을 둔다.

- 모든 예약 조회는 현재 사용자 범위를 검사한다.
- 시간은 저장 시 UTC, 표시 시 사용자 시간대를 쓴다.
- API 오류는 공통 응답 형식을 유지한다.
- UI 변경은 키보드 흐름을 검증한다.

리뷰 결과가 어느 규칙을 근거로 했는지 확인한다.

---

## Auto-review와 사람 리뷰

Auto-review는 승인 경계나 정책 검토를 보조할 수 있지만:

- Sandbox 범위를 넓히지 않는다.
- 제품 요구사항을 대신 확정하지 않는다.
- 최종 merge 책임을 가져가지 않는다.
- 모든 논리 오류를 발견한다고 보장하지 않는다.

고위험 변경은 독립된 사람 리뷰와 테스트가 필요하다.

---

## PR에 남길 증거

- 문제와 해결 방식
- 변경 범위와 비범위
- 테스트 명령과 결과
- UI 변경 스크린샷
- migration·보안·성능 영향
- 미검증 항목과 후속 작업

Codex가 작성한 PR 설명도 실제 diff와 일치하는지 검토한다.

---

## 협업 도구 연동

GitHub·GitLab·Slack·Linear 등을 연결할 때:

- 읽기와 쓰기 권한을 구분한다.
- 대상 저장소·채널·프로젝트를 확인한다.
- 게시·코멘트·상태 변경은 실행 전 초안을 검토한다.
- 조직 정책과 데이터 공개 범위를 따른다.

연동이 없으면 동일한 내용을 로컬 Markdown으로 제출한다.

---

## 실습

1. 제공된 branch를 기준 branch와 비교한다.
2. 리뷰 우선순위와 출력 형식을 지정한다.
3. Finding의 코드 근거를 직접 확인한다.
4. 유효한 Finding 하나를 수정하고 테스트한다.
5. PR 설명과 리뷰 답변 초안을 작성한다.

---

## 평가 체크

- [ ] 리뷰 기준 범위가 정확하다.
- [ ] Finding에 실패 시나리오와 코드 근거가 있다.
- [ ] 오탐을 그대로 수정하지 않았다.
- [ ] 수정 후 회귀 테스트를 실행했다.
- [ ] PR 설명이 실제 diff와 검증 결과와 일치한다.
