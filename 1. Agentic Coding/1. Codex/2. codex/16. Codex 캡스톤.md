# Codex 캡스톤

10개 이상의 기능 영역을 연결해 검증된 수직 웹 기능 완성하기

---

## 프로젝트 목표

`동네 클래스 예약 서비스`에 작은 수직 기능 하나를 완성한다.

예시:

- 클래스 조회와 예약
- 예약 취소와 정원 복구
- 대기 신청과 알림 상태
- 운영자용 예약 현황 조회

화면만 만드는 것이 아니라 UI→API→데이터→테스트→PR까지 연결한다.

---

## 필수 기능 영역

다음 중 10개 이상을 사용한다.

1. CLI·IDE·Desktop app·Cloud 중 2개 이상
2. Local·Worktree·Cloud 중 2개 이상
3. Plan Mode 또는 Goal
4. `AGENTS.md`
5. config·Profile·Rule 중 하나 이상
6. Sandbox와 승인 판단
7. 이미지 또는 웹 검색 컨텍스트
8. 터미널과 테스트
9. Code review와 PR
10. Skill·Plugin·MCP 중 하나 이상
11. Subagent 또는 Custom agent
12. Hook·`codex exec`·GitHub Action 중 하나 이상

---

## 1단계: 문제와 범위

작성할 것:

- 사용자 문제와 성공 지표
- 기능 범위와 비목표
- 정상·예외 시나리오
- 기술·보안 제약
- 완료 기준과 미완료 기준

Codex가 작성한 내용을 기획 산출물과 대조해 사람이 확정한다.

---

## 2단계: 실행 전략

결정할 것:

- 어떤 작업을 CLI·IDE·App·Cloud에 배치할지
- Local과 Worktree를 어떻게 나눌지
- 어떤 탐색을 Subagent에 맡길지
- 필요한 Sandbox와 승인 지점
- 진행 상황을 언제 보고받을지

선택한 기능의 개수보다 선택 이유가 중요하다.

---

## 3단계: 작업 계약

저장소에 준비한다.

- `AGENTS.md`
- 실제 build·lint·test 명령
- 코드 리뷰 규칙
- 완료 보고 형식
- 필요하면 개발·리뷰 Profile

지침의 명령을 직접 실행해 유효성을 확인한다.

---

## 4단계: 구현

권장 순서:

1. 코드 흐름과 기존 패턴 탐색
2. API·데이터 계약 확인
3. 실패 테스트 또는 재현 작성
4. 최소 수직 기능 구현
5. 상태·오류·권한 처리
6. 가까운 테스트부터 검증 범위 확대

각 의미 단위가 끝날 때 diff를 검토한다.

---

## 5단계: 독립 검증

- 구현 agent와 다른 관점의 리뷰
- 정확성·보안·접근성 Finding
- 브라우저 수동 검증과 스크린샷
- 단위·통합·E2E 테스트
- 로그·종료 코드·미검증 항목

Subagent의 결론도 실제 코드와 명령으로 교차 확인한다.

---

## 6단계: 자동화

다음 중 하나 이상을 구현한다.

- 반복 검증 Skill
- 읽기 전용 MCP 조회
- 안전 정책 Hook
- 구조화된 `codex exec` 리뷰
- GitHub Action 품질 검사

자동화가 실패할 때 merge를 허용할지 차단할지 명시한다.

---

## 7단계: PR과 발표

PR에 포함:

- 문제와 해결 방식
- 변경 범위와 주요 결정
- 화면 캡처 또는 동작 증거
- 테스트 명령과 결과
- 권한·보안 판단
- 미검증 항목과 후속 작업

발표에서는 Codex가 틀렸던 지점과 사람이 개입한 근거도 설명한다.

---

## 필수 증거 패키지

```text
capstone-evidence/
├─ brief.md
├─ plan.md
├─ feature-usage.md
├─ commands-and-tests.md
├─ review-findings.md
├─ screenshots/
└─ retrospective.md
```

실제 비밀값·개인정보·불필요한 전체 로그는 포함하지 않는다.

---

## 평가 기준

| 영역 | 배점 | 핵심 질문 |
|---|---:|---|
| Codex 기능 활용 | 30 | 기능 선택이 작업 목적과 맞는가? |
| 구현 품질 | 20 | 요구사항과 기존 구조를 지켰는가? |
| 검증 품질 | 25 | 테스트·브라우저·로그 증거가 충분한가? |
| 권한·보안 | 10 | 최소 권한과 승인 판단이 적절한가? |
| Git·리뷰 | 10 | diff·commit·PR이 검토 가능한가? |
| 회고 | 5 | 한계와 사람 개입을 구체적으로 설명하는가? |

---

## 감점 기준

- 실행하지 않은 테스트를 통과했다고 보고
- 실제 자격증명이나 개인정보 포함
- 요구 범위 밖 대규모 변경
- Codex 결과를 검토하지 않고 merge
- 기능 개수를 채우기 위한 불필요한 도구 사용
- 실패 기록과 미검증 항목 누락

---

## 최종 체크리스트

- [ ] 기능 영역 10개 이상과 선택 이유를 기록했다.
- [ ] 목표·범위·완료 기준이 구현과 일치한다.
- [ ] 모든 diff를 사람이 검토했다.
- [ ] 테스트와 브라우저 검증의 실제 증거가 있다.
- [ ] 권한·외부 전송·비밀값을 점검했다.
- [ ] PR과 회고에서 Codex의 한계를 설명했다.
