# 프롬프트와 실행 제어

Plan·Goal·모델·추론·컨텍스트를 의도적으로 다루기

---

## 오늘의 목표

- 구현 요청을 검증 가능한 개발 브리핑으로 바꾼다.
- Plan Mode와 Goal을 용도에 맞게 사용한다.
- 모델과 추론 수준을 작업 위험에 맞춘다.
- 긴 Chat의 컨텍스트를 관리한다.

---

## 좋은 개발 브리핑의 여섯 요소

1. 목표: 무엇이 달라져야 하는가?
2. 범위: 어디를 변경할 수 있는가?
3. 비목표: 무엇은 하지 않는가?
4. 제약: 호환성·보안·성능 조건은?
5. 완료 기준: 무엇을 확인하면 끝인가?
6. 보고 형식: 어떤 증거를 남길 것인가?

---

## 요청 예시

```text
목표: 로그인한 사용자가 클래스를 예약할 수 있게 한다.
범위: reservation UI, API client, 관련 테스트
비목표: 결제와 관리자 기능
제약: 기존 디자인 토큰과 오류 응답 형식 유지
완료 기준: 정상·마감·중복 예약 테스트 통과
보고: 변경 파일, 실행 명령, 결과, 미검증 항목
```

---

## Plan Mode

구현 전에 불확실성과 영향 범위를 드러낼 때 사용한다.

계획에서 확인할 항목:

- 요구사항의 모호함
- 영향 파일과 시스템 경계
- API·DB 계약 변화
- 테스트 전략
- 롤백 또는 되돌리기 방법

계획을 승인했다는 것은 모든 구현 판단을 백지 위임했다는 뜻이 아니다.

---

## Goal

Goal은 여러 턴과 긴 실행에 걸쳐 유지해야 하는 완료 목표에 적합하다.

좋은 Goal:

- 종료 조건이 측정 가능하다.
- 진행 중 보고 시점이 있다.
- 멈추고 질문할 조건이 있다.
- 허용된 변경 범위가 분명하다.

작은 한 줄 수정에는 일반 Chat이 더 단순하다.

---

## 모델과 추론 수준

| 작업 | 선택 기준 |
|---|---|
| 단순 탐색·문구 수정 | 빠른 응답과 낮은 비용 |
| 다중 파일 구현 | 충분한 코드 이해와 계획 능력 |
| 복잡한 버그·설계 | 높은 추론 수준과 더 많은 검증 |
| 보안·대규모 변경 | 강한 모델 + 좁은 권한 + 사람 리뷰 |

모델이 강할수록 권한을 넓혀야 하는 것은 아니다.

---

## 컨텍스트 관리

긴 Chat에서 나타나는 신호:

- 이미 폐기한 결정을 다시 따른다.
- 현재 목표와 무관한 파일을 수정한다.
- 요약이 오래된 코드 상태를 전제로 한다.

대응:

- `/status`로 상태 확인
- `/compact`로 핵심 결정 압축
- 목표가 달라졌다면 새 Chat으로 분리
- 중요한 계약은 저장소 문서와 `AGENTS.md`에 기록

---

## 강사 시연

모호한 요청을 단계적으로 개선한다.

```text
예약 기능 만들어줘.
```

→ 범위·비목표·완료 기준 추가

→ Plan Mode에서 영향 분석

→ 승인 후 구현

→ 완료 증거와 미검증 항목 보고

---

## 실습

1. 제공된 PRD를 여섯 요소의 개발 브리핑으로 변환한다.
2. `/plan`으로 구현 계획을 만든다.
3. 빠진 위험과 테스트를 사람이 보완한다.
4. 작은 구현은 일반 Chat, 긴 구현은 Goal로 나눈다.
5. 어떤 모델·추론 수준을 선택했는지 근거를 기록한다.

---

## 평가 기준

- 계획이 코드 구조를 근거로 하는가?
- 비목표와 중단 조건이 있는가?
- 테스트가 요구사항의 예외를 포함하는가?
- 모델 선택이 작업 난이도와 비용을 고려하는가?
- 미검증 항목을 성공으로 표현하지 않았는가?
