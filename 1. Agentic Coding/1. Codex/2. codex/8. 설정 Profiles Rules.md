# 설정·Profiles·Rules

Codex의 반복 동작을 안전한 기본값으로 만들기

---

## 오늘의 목표

- 사용자 설정과 프로젝트 설정을 구분한다.
- `config.toml`의 주요 설정 영역을 이해한다.
- 목적별 Profile을 분리한다.
- Rules와 feature flags를 보수적으로 운영한다.

---

## 설정의 범위

| 범위 | 용도 | 예시 |
|---|---|---|
| 사용자 | 모든 저장소의 개인 기본값 | 모델, 추론 수준, 기본 권한 |
| 프로젝트 | 신뢰한 저장소의 공통 설정 | MCP, hooks, 로컬 환경 |
| 세션 | 이번 Chat의 일시적 선택 | 모델·권한·실행 모드 변경 |
| 조직 관리 | 관리자가 강제하는 정책 | 모델 허용 목록, 연결·보안 제한 |

더 구체적인 설정이 항상 조직 정책을 우회할 수 있는 것은 아니다.

---

## config.toml 핵심 영역

```toml
model = "<현재 허용된 모델>"
model_reasoning_effort = "medium"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

정확한 키와 허용 값은 설치된 버전의 문서와 설정 화면에서 확인한다.

---

## Profile 설계

작업마다 필요한 권한과 목적이 다르다.

| Profile | 목적 | 권장 성격 |
|---|---|---|
| dev | 로컬 구현과 테스트 | workspace-write, 승인 요청 |
| review | 읽기 전용 코드 검토 | read-only, 높은 추론 |
| ci | 비대화형 반복 검사 | 고정 출력, 실패 폐쇄 |

Profile 이름만 믿지 말고 실제 설정을 검토한다.

---

## Rules

Rules는 특정 명령 패턴에 대한 정책을 좁게 정의할 때 사용한다.

- 안전한 읽기 명령 허용
- 패키지 설치는 승인 요청
- 위험한 삭제·강제 push 차단

넓은 셸 전체를 허용하면 작은 편의 때문에 큰 권한을 주게 된다. 실제 필요한 명령 prefix만 대상으로 한다.

---

## Feature flags와 maturity

기능은 안정·베타·실험 단계가 다를 수 있다.

확인할 것:

- 현재 버전에서 제공되는가?
- 기본 활성화인가?
- 조직 정책이 허용하는가?
- 실패 시 되돌릴 수 있는가?
- 팀 전체가 같은 설정을 쓰는가?

실험 기능은 핵심 배포 경로의 필수 조건으로 만들지 않는다.

---

## 설정 변경 절차

1. 해결하려는 문제를 한 문장으로 적는다.
2. 가장 좁은 범위의 설정을 선택한다.
3. 기존 파일을 백업하거나 diff로 확인한다.
4. 한 항목만 바꾸고 새 세션에서 검증한다.
5. 효과와 부작용을 기록한다.

설정이 안 먹는다고 바로 권한을 최대로 올리지 않는다.

---

## 강사 시연

- 기본 개발 설정 확인
- 읽기 전용 리뷰 Profile 실행
- 네트워크가 필요한 명령에서 승인 흐름 관찰
- 차단 Rule에 걸리는 위험 명령 확인
- 세션 `/status`와 설정 파일 값 비교

---

## 실습

1. 현재 설정 위치와 적용 범위를 찾는다.
2. `dev`, `review`, `ci` 세 목적의 설정표를 작성한다.
3. 실제로 `review`를 읽기 전용으로 실행한다.
4. 허용·승인·차단할 명령을 각각 2개 선정한다.
5. 실험 기능 하나를 조사하고 도입 여부를 결정한다.

---

## 제출물

- 설정 범위 다이어그램
- 비밀값을 제거한 설정 예시

- Rule 테스트 결과
- feature flag 도입 또는 보류 근거
