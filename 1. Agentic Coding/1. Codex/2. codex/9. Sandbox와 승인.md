# Sandbox와 승인

Codex에게 필요한 만큼만 권한 주기

---

## 오늘의 목표

- Sandbox와 승인 정책의 차이를 설명한다.
- 작업별로 적절한 권한 모드를 선택한다.
- 네트워크·외부 서비스·파괴적 작업 요청을 판단한다.
- 비밀정보와 사용자 변경을 보호한다.

---

## 두 개의 안전장치

- Sandbox: 기술적으로 어디까지 읽고·쓰고·실행할 수 있는가
- 승인 정책: 경계를 넘을 때 누가 언제 허용하는가

Sandbox가 좁아도 무조건 안전한 것은 아니며, 승인이 많아도 내용을 읽지 않으면 통제가 아니다.

---

## Sandbox 모드

| 모드 | 허용 범위 | 적합한 상황 |
|---|---|---|
| `read-only` | 검사 중심, 쓰기 제한 | 계획·탐색·리뷰 |
| `workspace-write` | 작업공간 안에서 읽기·쓰기 | 일반 로컬 개발 |
| `danger-full-access` | Sandbox 제한 없음 | 격리된 신뢰 환경의 예외적 작업 |

기본 선택은 작업을 완료할 수 있는 가장 좁은 모드다.

---

## 승인 요청을 읽는 법

승인 전에 네 질문을 확인한다.

1. 무엇을 실행하려는가?
2. 정확히 어느 파일·서비스·데이터가 대상인가?
3. 왜 현재 Sandbox 밖의 권한이 필요한가?
4. 실패하거나 악용되면 되돌릴 수 있는가?

설명이 불명확하면 거부하고 더 좁은 대안을 요청한다.

---

## 네트워크 접근

필요할 수 있는 예:

- 패키지 다운로드
- 공식 문서 검색
- 원격 API 테스트
- Git push와 PR 생성

확인할 것:

- 도메인과 전송 데이터
- 인증정보 사용 여부
- 읽기인가 쓰기인가
- 외부 콘텐츠의 프롬프트 인젝션 가능성

---

## 비밀정보

- `.env` 내용을 Chat에 그대로 붙이지 않는다.
- 자격증명 파일을 읽도록 지시하지 않는다.
- 로그와 오류 메시지의 토큰·개인정보를 제거한다.
- Cloud setup secret과 실행 단계의 노출 범위를 구분한다.
- 예제는 가짜 키와 샘플 데이터로 진행한다.

비밀값이 노출되었다면 파일 삭제만 하지 말고 자격증명도 폐기·교체해야 한다.

---

## 파괴적 작업

항상 별도 확인이 필요한 예:

- 재귀 삭제와 대량 이동
- `git push --force`
- 운영 DB 수정
- 배포·결제·메시지 발송
- 대규모 자동 포맷 또는 마이그레이션

대상 목록 → 영향 분석 → 백업·복구 방법 → dry run → 실행 순서를 지킨다.

---

## 강사 시연

세 요청을 비교한다.

1. 파일 구조 읽기: `read-only`
2. 테스트 수정: `workspace-write`
3. 새 패키지 설치: 네트워크 승인

각 요청에서 `/status`, 승인 메시지, 변경 결과를 함께 확인한다.
