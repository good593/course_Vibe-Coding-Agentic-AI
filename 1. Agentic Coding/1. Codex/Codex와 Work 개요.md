# Codex와 ChatGPT Work 개요

---

## 먼저 생각해 보기

다음 세 가지 부탁은 모두 AI에게 할 수 있습니다.

- “반복문이 무엇인지 설명해 줘.”
- “첨부한 설문 결과를 분석해 발표 자료를 만들어 줘.”
- “이 프로젝트의 로그인 오류를 찾아 고치고 테스트해 줘.”

하지만 필요한 AI의 역할은 서로 다릅니다.

> 핵심은 “어떤 AI가 더 좋은가?”가 아니라  
> **“내가 원하는 결과물은 무엇인가?”** 입니다.

---

## Chat, Work, Codex를 한 문장으로

| 구분 | 한 문장 설명 | 대표 결과 |
|---|---|---|
| Chat | 함께 대화하며 생각을 발전시키는 AI | 답변, 설명, 아이디어 |
| ChatGPT Work | 자료와 도구를 사용해 업무 결과물을 만드는 AI | 문서, 표, 발표 자료 |
| Codex | 코드와 개발 도구를 사용해 소프트웨어 작업을 수행하는 AI | 코드 변경, 테스트 결과, 리뷰 |

세 기능은 경쟁 관계라기보다 **목적이 다른 작업 방식**에 가깝습니다.

---

# 1. AI 에이전트란?

---

## 챗봇과 에이전트의 차이

### 챗봇

질문을 받으면 답변을 생성합니다.

`질문 → 답변`

### 에이전트

목표를 받으면 필요한 자료와 도구를 사용하고, 결과를 확인하며 여러 단계를 수행합니다.

`목표 → 조사 → 계획 → 실행 → 확인 → 수정 → 결과`

> 에이전트는 “말을 잘하는 AI”에서 한 걸음 더 나아가  
> **도구를 사용해 일을 진행하는 AI**입니다.

---

## 에이전트를 ‘신입 팀원’으로 생각해 보기

신입 팀원에게 “행사 준비해 주세요”라고만 말하면 어려워합니다.

다음 정보가 필요합니다.

- 어떤 행사를 준비하는가?
- 누구를 위한 행사인가?
- 예산과 마감일은 언제인가?
- 사용할 수 있는 자료는 무엇인가?
- 무엇을 제출하면 완료인가?

AI 에이전트도 같습니다. 능력이 좋아도 **목표와 기준이 모호하면 엉뚱한 방향으로 열심히 일할 수 있습니다.**

---

## 에이전트의 기본 작동 흐름

1. **목표 이해**: 사용자가 원하는 결과 파악
2. **맥락 수집**: 파일, 코드, 문서 등 필요한 정보 확인
3. **계획 수립**: 해야 할 일을 작은 단계로 나눔
4. **도구 사용**: 파일 읽기·수정, 명령 실행, 검색 등
5. **결과 관찰**: 오류나 빠진 내용 확인
6. **재시도**: 필요하면 계획이나 결과 수정
7. **보고**: 수행 내용과 남은 위험을 사용자에게 전달

이 반복 구조를 흔히 **에이전트 루프(agent loop)**라고 부릅니다.

# [2. Codex 이해하기](https://learn.chatgpt.com/docs/codex/cli)

---

## Codex란?

Codex는 OpenAI의 **코딩 에이전트**입니다.

단순히 코드 한 줄을 추천하는 것을 넘어 다음과 같은 개발 작업을 수행할 수 있습니다.

- 프로젝트 구조와 기존 코드 이해
- 새로운 기능 구현
- 버그 원인 조사와 수정
- 테스트 및 개발 명령 실행
- 코드 리뷰와 개선안 제시
- 변경된 파일과 검증 결과 보고

공식 문서도 Codex의 시작 작업으로 코드 탐색, 기능 개발, 코드 리뷰, 오류 수정을 제시합니다.

---

## 자동 완성과 Codex의 차이

### 코드 자동 완성

```python
def add(a, b):
    return # 다음 코드를 추천
```

현재 작성 중인 코드의 **다음 부분**을 예측하는 데 집중합니다.

### Codex

> “장바구니 총액이 음수가 되는 버그를 찾아 고치고, 같은 문제가 다시 생기지 않도록 테스트를 추가해 줘.”

관련 파일을 찾고, 코드의 흐름을 이해하고, 수정하고, 테스트하는 **전체 작업**을 수행합니다.

---

## Codex가 일할 때 사용하는 것

| 사용하는 정보·도구 | 하는 일 |
|---|---|
| 프로젝트 파일 | 코드 구조와 현재 동작 이해 |
| 검색 도구 | 관련 함수, 설정, 오류 위치 탐색 |
| 편집 도구 | 코드와 문서 수정 |
| 터미널 | 빌드, 테스트, 린트 등 명령 실행 |
| Git 정보 | 기존 변경과 자신의 변경 구분 |
| 테스트 결과 | 수정이 실제로 동작하는지 확인 |

따라서 Codex의 결과는 보통 답변 하나가 아니라 **파일 변경 + 실행 결과 + 설명**입니다.

---

## Codex 작업 예시

### 사용자 요청

> 회원가입 버튼을 눌러도 반응이 없습니다. 원인을 찾아 수정하고 테스트해 줘.

### 가능한 작업 흐름

1. 회원가입 화면과 이벤트 처리 코드 탐색
2. 버튼 클릭 이벤트가 연결되지 않은 원인 발견
3. 이벤트 처리 코드 수정
4. 관련 테스트 추가 또는 기존 테스트 실행
5. 실패하면 오류를 읽고 다시 수정
6. 변경 파일과 테스트 결과 보고

사람은 마지막에 화면 동작, 변경 코드, 테스트 결과를 검토합니다.

---

## Codex를 사용할 수 있는 환경

| 환경 | 잘 맞는 상황 |
|---|---|
| 데스크톱 앱 | 프로젝트와 여러 작업을 한곳에서 관리할 때 |
| CLI | 터미널에서 저장소와 개발 도구를 직접 사용할 때 |
| IDE 확장 | 열어 둔 코드와 선택 영역을 중심으로 작업할 때 |
| 클라우드 환경 | 격리된 환경에서 오래 걸리는 작업을 맡길 때 |

처음에는 익숙한 IDE나 데스크톱 앱으로 시작하고, 터미널에 익숙해지면 CLI를 함께 사용해도 좋습니다.

---

## Codex가 특히 잘 맞는 요청

- “이 저장소의 실행 방법과 폴더 구조를 설명해 줘.”
- “검색 결과가 없을 때 안내 문구를 표시해 줘.”
- “이 오류 로그의 원인을 찾고 최소 범위로 수정해 줘.”
- “중복된 코드를 함수로 정리하고 기존 테스트를 통과시켜 줘.”
- “이 변경에서 버그나 보안 문제가 있는지 리뷰해 줘.”

공통점은 **코드베이스를 읽고 실제 개발 결과를 만들어야 한다는 것**입니다.

# [3. ChatGPT Work 이해하기](https://learn.chatgpt.com/docs/get-started-with-work)

---

## ChatGPT Work란?

ChatGPT Work는 ChatGPT에 **결과가 분명한 업무를 맡기고, 검토 가능한 산출물을 받는 작업 방식**입니다.

- 여러 파일과 자료를 읽기
- 필요한 정보 조사하고 정리하기
- 문서, 스프레드시트, 발표 자료 만들기
- 플러그인과 승인된 도구 사용하기
- 반복되는 업무를 정기적으로 수행하기

짧은 답변보다 **완성된 업무 결과물**이 필요할 때 적합합니다.

---

## Chat과 Work의 차이

### Chat에 잘 맞는 요청

> “마케팅 퍼널이 무엇인지 쉽게 설명해 줘.”

대화 속 설명이 곧 결과입니다.

### Work에 잘 맞는 요청

> “첨부한 고객 인터뷰 20개를 분석해 공통 불편 사항을 정리하고, 제품 회의용 8장 발표 자료를 만들어 줘.”

자료 확인과 여러 단계의 작업을 거쳐 **사용자가 검토할 파일**을 만듭니다.

---

## Work 작업 예시

### 사용자 요청

> 지난달 만족도 조사 파일을 분석해 팀 회의용 보고서를 만들어 줘.

### 가능한 작업 흐름

1. 첨부된 설문 파일 확인
2. 응답 정리와 주요 수치 계산
3. 자주 등장한 의견 분류
4. 표와 그래프로 핵심 내용 표현
5. 결론과 다음 행동 제안
6. 검토 가능한 보고서 파일 전달

사람은 수치, 근거, 누락된 응답, 과도한 해석이 없는지 확인합니다.

---

## Work와 플러그인

플러그인은 Work가 외부 서비스의 정보와 기능을 사용하도록 연결합니다.

예를 들면 다음과 같습니다.

- 클라우드 저장소에서 회의 자료 찾기
- 이메일에서 고객 요청 모으기
- 일정에서 다음 회의 확인하기
- 프로젝트 관리 도구에서 진행 상황 정리하기

플러그인을 사용한다고 모든 권한이 자동으로 열리는 것은 아닙니다. **연결된 범위와 승인된 행동 안에서 사용**해야 합니다.

---

## Work의 로컬 작업과 클라우드 작업

### 로컬

- 내 컴퓨터의 파일이나 앱이 필요한 작업
- 컴퓨터가 켜져 있고 앱이 실행되는 동안 작업

### 클라우드

- 컴퓨터를 닫아도 계속 진행해야 하는 작업
- 웹이나 모바일에서 이어서 확인할 작업
- 장시간 조사나 정기 모니터링 작업

작업에 필요한 자료가 어디에 있는지에 따라 선택합니다.

---

## Work가 특히 잘 맞는 요청

- “이 회의록을 바탕으로 결정 사항과 담당자를 정리해 줘.”
- “세 업체의 견적서를 비교하는 스프레드시트를 만들어 줘.”
- “조사 자료를 10장 발표 자료로 구성해 줘.”
- “매주 월요일 프로젝트 현황을 모아 주간 보고서를 갱신해 줘.”
- “여러 자료를 종합해 의사결정용 요약 문서를 만들어 줘.”

공통점은 **자료와 도구를 이용한 다단계 업무 결과물**이 필요하다는 것입니다.

## Chat·Work·Codex 비교

| 질문 | Chat | Work | Codex |
|---|:---:|:---:|:---:|
| 설명이나 아이디어가 필요한가? | ◎ | ○ | △ |
| 완성된 업무 파일이 필요한가? | △ | ◎ | ○ |
| 코드베이스를 이해해야 하는가? | △ | △ | ◎ |
| 코드를 직접 수정해야 하는가? | △ | △ | ◎ |
| 여러 자료와 업무 도구가 필요한가? | △ | ◎ | ○ |
| 테스트와 개발 명령을 실행해야 하는가? | ✕ | △ | ◎ |

`◎ 매우 적합 / ○ 가능 / △ 제한적 / ✕ 목적과 다름`

> 기능이 일부 겹칠 수 있으므로 **주요 결과물**을 기준으로 선택합니다.

---

## 10초 선택법

### 1. 대화 속 답변이면 충분한가?

→ **Chat**

### 2. 문서·표·발표 자료 같은 업무 결과물이 필요한가?

→ **Work**

### 3. 실행되고 테스트된 코드 변경이 필요한가?

→ **Codex**

결과물이 둘 이상이면 Work와 Codex를 이어서 사용할 수 있습니다.

---

## 하나의 프로젝트에서 함께 사용하기

### 예: 학교 축제 안내 웹사이트 만들기

1. **Chat**: 대상 사용자와 필요한 기능을 함께 생각하기
2. **Work**: 회의록과 설문을 분석해 요구사항 문서 만들기
3. **Codex**: 웹사이트 구현, 테스트, 오류 수정
4. **Work**: 완성된 기능을 소개하는 발표 자료 만들기

도구를 나누어 쓰면 각 단계의 결과가 다음 단계의 좋은 입력이 됩니다.

---

## 상황 퀴즈

다음 작업에는 무엇이 가장 잘 맞을까요?

1. “API가 무엇인지 중학생도 이해하게 설명해 줘.” -> `Chat 사용` 
2. “첨부한 매출 파일 세 개를 비교해 월간 보고서를 만들어 줘.” -> `Work 사용`
3. “결제 API 호출이 실패하는 원인을 찾아 수정하고 테스트해 줘.” -> `Codex 사용`
4. “졸업 작품의 아이디어를 다섯 개 제안해 줘.” -> `Chat 사용`
5. “완성된 앱의 기능을 소개하는 발표 자료를 만들어 줘.” -> `Work 사용`

# 5. 일을 잘 맡기는 방법

---

## 좋은 요청의 5가지 요소

| 요소 | 확인할 질문 |
|---|---|
| 목표 | 무엇을 만들거나 해결해야 하는가? |
| 맥락·자료 | 어떤 파일과 정보를 사용해야 하는가? |
| 범위·제약 | 무엇을 해도 되고, 하면 안 되는가? |
| 완료 기준 | 어떤 상태가 되면 끝난 것인가? |
| 보고 방식 | 무엇을 어떻게 알려 줘야 하는가? |

긴 프롬프트보다 **판단 기준이 분명한 요청**이 더 중요합니다.

---

## Codex 요청: 나쁜 예와 좋은 예

### 나쁜 예

> 로그인 고쳐 줘.

어떤 증상인지, 어디까지 수정해도 되는지, 완료 기준이 무엇인지 알기 어렵습니다.

### 좋은 예

> 이메일 로그인 후 홈 화면으로 이동하지 않는 문제를 조사해 줘. 기존 인증 API는 변경하지 말고 프런트엔드 범위에서 최소 수정해 줘. 관련 테스트를 실행하고, 변경 파일·원인·테스트 결과를 요약해 줘.

목표, 범위, 제약, 검증, 보고 방식이 들어 있습니다.

---

## Work 요청: 나쁜 예와 좋은 예

### 나쁜 예

> 고객 조사 발표 자료 만들어 줘.

### 좋은 예

> 첨부한 인터뷰 기록과 설문 결과만 사용해 제품 리더 회의용 8장 발표 자료를 만들어 줘. 가장 많이 나온 문제 3개와 근거를 제시하고, 사실과 제안을 구분해 줘. 근거가 부족한 내용은 표시하고 최종본 전에 초안을 먼저 보여 줘.

자료, 대상, 형식, 품질 기준, 승인 시점이 분명합니다.

# 6. 사람의 역할과 안전

## AI에게 맡겨도 책임은 사람에게 있다

AI 에이전트는 빠르지만 다음과 같은 실수를 할 수 있습니다.

- 요구사항을 잘못 해석하기
- 존재하지 않는 사실이나 원인을 추측하기
- 필요한 파일을 빠뜨리기
- 기존 기능을 망가뜨리기
- 그럴듯하지만 틀린 수치나 결론 만들기

따라서 “완료했습니다”라는 문장보다 **결과를 뒷받침하는 증거**를 확인해야 합니다.

---

## 권한은 필요한 만큼만

AI 에이전트가 할 수 있는 행동이 많을수록 편리하지만 위험도 커집니다.

- 파일을 읽기만 하면 되는가?
- 파일 수정까지 필요한가?
- 인터넷 접속이 필요한가?
- 외부 서비스에 내용을 전송해도 되는가?
- 삭제, 결제, 게시 같은 중요한 행동인가?

중요하거나 되돌리기 어려운 행동은 **실행 전에 멈추고 사람의 승인을 받도록** 요청합니다.

---

## Codex 결과 확인 체크리스트

- 변경된 파일이 요청 범위 안에 있는가?
- 코드를 직접 읽어 보았는가?
- 테스트가 실제로 실행되었는가?
- 테스트 통과 개수와 실패 내용을 확인했는가?
- 기존 기능에 영향을 주지 않는가?
- 비밀번호나 API 키가 코드에 들어가지 않았는가?
- 검증하지 못한 항목이 보고되어 있는가?

Git diff와 테스트 로그는 Codex 작업을 확인하는 중요한 증거입니다.

---

## Work 결과 확인 체크리스트

- 사용한 출처와 파일이 맞는가?
- 수치가 원본 자료와 일치하는가?
- 사실과 AI의 해석이 구분되어 있는가?
- 중요한 내용이 빠지지 않았는가?
- 대상 독자와 목적에 맞는가?
- 외부 공유 전 개인정보와 민감 정보를 확인했는가?
- 자동 전송이나 게시 전에 최종 승인했는가?

예쁜 결과물도 근거가 틀리면 좋은 결과가 아닙니다.

---

## 자주 하는 오해

### “Codex는 한 번에 완벽한 코드를 만든다.”

아닙니다. 구현과 테스트, 검토를 반복해야 합니다.

### “Work는 긴 답변을 주는 Chat이다.”

Work의 핵심은 길이가 아니라 자료와 도구를 사용해 **검토 가능한 결과물을 완성하는 것**입니다.

### “에이전트가 알아서 하니 사람은 필요 없다.”

사람은 목표, 권한, 품질 기준을 정하고 결과를 승인합니다.

### “프롬프트는 길수록 좋다.”

길이보다 목표와 완료 기준이 명확해야 합니다.
