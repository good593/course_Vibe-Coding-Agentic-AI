# Codex 강의 커리큘럼

> 상위 과정: 바이브 코딩 & Agentic AI 실전 (`1. Agentic Coding`)
> 이 모듈의 목표: "AI에게 코드를 대신 써 달라고 하기"를 넘어, **Codex에 안전하게 위임하고, 결과를 검증하며, 개인과 팀의 개발 워크플로우에 통합**할 수 있는 실무 감각을 기르는 것.

전체 12차시(0~11), 차시당 2~3시간, 총 약 30시간 분량. 주 2회 진행 시 약 6주 과정.

> [!NOTE]
> 이 문서는 2026-09-01 기준 공식 OpenAI 문서를 바탕으로 구성했다. Codex의 모델, 요금제, 명령, 제공 기능은 바뀔 수 있으므로 수업 직전 [Codex 공식 문서](https://learn.chatgpt.com/docs)를 다시 확인한다.

---

## 학습 목표 (수료 시 학생이 할 수 있어야 하는 것)

1. Codex CLI와 IDE 확장을 설치하고 로컬 프로젝트에서 작업을 위임할 수 있다
2. Chat·ChatGPT Work·Codex의 역할을 구분하고, 작업 성격에 따라 Work·CLI·IDE·Codex 클라우드 중 적절한 환경을 선택할 수 있다
3. 좋은 브리핑과 `AGENTS.md`로 프로젝트 맥락, 제약 조건, 완료 기준을 전달할 수 있다
4. Plan Mode, 샌드박스, 승인 정책, Git 체크포인트로 **에이전트의 행동 범위를 통제**할 수 있다
5. Git/GitHub 워크플로우(브랜치, 커밋, 리뷰, PR)를 Codex와 함께 수행할 수 있다
6. "Codex가 완료했다고 말한 것"을 그대로 믿지 않고 테스트·로그·diff로 직접 검증할 수 있다
7. Skills, MCP, Subagents를 이용해 반복 작업과 복합 작업을 확장할 수 있다
8. `codex exec`와 GitHub Action을 이용한 비대화형 자동화의 기본 구조를 설계할 수 있다
9. 모델·추론 수준·컨텍스트·권한을 작업 위험과 비용에 맞게 선택할 수 있다

## 사전 준비물

- Codex를 사용할 수 있는 ChatGPT 계정 또는 조직에서 제공한 인증 수단
- Git과 터미널을 사용할 수 있는 PC
- GitHub 계정, `gh` CLI 설치 가능 환경
- VS Code 또는 호환 IDE (IDE 확장 실습용)
- npm 방식으로 CLI를 설치할 경우 Node.js/npm
- 실습용 Git 저장소: 중요한 개인 파일이나 실제 운영 비밀값이 없는 별도 저장소 권장

## 0차시. 오리엔테이션 — Chat·Work·Codex와 Agentic Coding

- **목표**: Chat, ChatGPT Work, Codex의 역할과 코드 자동완성·코딩 에이전트의 차이를 구분한다
- **내용**
  - [ChatGPT Work](https://learn.chatgpt.com/docs/get-started-with-work)를 포함한 제품 지도
    - **Chat**: 질문, 설명, 브레인스토밍, 짧은 초안처럼 대화 자체가 중심인 작업
    - **Work**: 파일·플러그인·승인된 도구를 사용해 문서, 발표자료, 스프레드시트, 분석 보고서, 반복 업데이트처럼 **검토 가능한 결과물**을 완성하는 일상 업무
    - **Codex**: 코드베이스를 이해하고, 코드를 수정하고, 명령과 테스트를 실행하며, diff와 PR로 변경을 전달하는 소프트웨어 개발 업무
  - Work와 Codex는 완전히 단절된 제품이 아니다. 비코딩 업무에서는 핵심 능력이 겹치며, 차이는 주로 **결과물과 작업 경험의 중심**에 있다
  - 하나의 프로젝트 안에서도 Work로 요구사항·조사·보고서를 만들고, Codex로 구현·테스트·리뷰한 뒤, 다시 Work로 발표자료나 운영 문서를 만드는 연결 흐름
  - 자동완성 도구와 에이전트의 차이: 답변 생성 vs 파일 읽기 → 계획 → 수정 → 명령 실행 → 결과 관찰 → 재시도
  - Codex가 잘하는 일: 코드베이스 탐색, 기능 구현, 리팩터링, 테스트, 디버깅, 코드 리뷰, 반복 업무 자동화
  - Codex의 주요 실행 환경
    - [CLI](https://learn.chatgpt.com/docs/codex/cli): 터미널에서 로컬 저장소와 도구를 직접 사용하는 작업
    - [IDE 확장](https://learn.chatgpt.com/docs/codex/ide): 열린 파일과 선택 영역을 활용한 짧고 집중된 수정
    - [Codex 클라우드](https://learn.chatgpt.com/docs/cloud): 격리된 환경에서 오래 걸리는 작업이나 여러 작업을 병렬로 위임
  - 에이전트가 강력한 이유와 위험한 이유: 넓은 행동 범위, 빠른 반복, 잘못된 가정의 증폭
  - 과정 전체의 원칙: **위임은 넓게 할 수 있어도, 책임과 검증은 사람이 가진다**
- **실습**: 하나의 프로젝트 요청을 Chat·Work·Codex에 각각 맡겨 보고, 대화 답변·업무 결과물·검증된 코드 변경의 차이를 비교하는 선택표 작성

## 1차시. 설치와 첫 실행 — 로컬 저장소에서 시작하기

- **목표**: Codex CLI와 IDE 확장을 준비하고, 현재 작업 범위와 권한을 확인한 뒤 첫 작업을 수행한다
- **내용**
  - [공식 CLI 설치 안내](https://learn.chatgpt.com/docs/codex/cli)에 따라 운영체제별 설치 방법 선택
    - 독립 설치 프로그램 사용
    - npm 사용 시 `npm install -g @openai/codex`
  - 프로젝트 디렉터리에서 `codex` 실행 후 ChatGPT 또는 제공된 인증 방식으로 로그인
  - IDE 확장 설치와 사이드바 열기, 열린 파일·선택 영역을 컨텍스트로 전달하는 법
  - 시작 시 반드시 확인할 것: 현재 디렉터리, Git 상태, 모델과 추론 수준, 샌드박스와 승인 정책
  - 기본 명령: `/status`, `/model`, `/permissions`, `/init`, `/review`
  - 작업 전후 Git 체크포인트를 만드는 이유
- **실습**: 실습 저장소에서 "이 프로젝트의 구조와 실행 방법을 설명해 줘. 아직 파일은 수정하지 마"라고 요청한 뒤, 작은 문서 수정 한 건을 맡기고 diff 확인

## 2차시. Codex에게 일을 시키는 법 — 프롬프트보다 좋은 브리핑

- **목표**: 모호한 지시를 맥락·제약·완료 기준이 포함된 실행 가능한 브리핑으로 바꾼다
- **내용**
  - 좋은 작업 요청의 6요소
    1. **목표**: 무엇을 왜 바꾸는가
    2. **범위**: 수정해도 되는 파일과 건드리지 말아야 할 영역
    3. **맥락**: 사용자, 현재 문제, 관련 코드와 문서
    4. **제약**: 기술 스택, 호환성, 스타일, 보안 요구사항
    5. **완료 기준**: 어떤 동작과 테스트를 통과해야 하는가
    6. **보고 방식**: 변경 요약, 검증 명령, 남은 위험
  - "로그인 만들어 줘"와 "세션 기반 로그인 추가, 기존 API 유지, 실패 테스트 포함"의 차이
  - 구현 전 탐색 요청: 관련 파일, 데이터 흐름, 테스트 명령을 먼저 찾게 하기
  - 큰 작업을 조사 → 계획 → 구현 → 검증 단위로 나누는 법
  - 진행 중 방향 수정: 잘못된 가정을 발견하면 즉시 멈추고 근거를 다시 확인시키기
- **실습**: 같은 기능을 모호한 한 줄과 6요소 브리핑으로 각각 요청하고 변경 범위·재작업 횟수·테스트 품질 비교

## 3차시. `AGENTS.md`와 `config.toml` — 프로젝트의 작업 계약 만들기

- **목표**: 반복 설명을 저장소 지침으로 고정하고, 지침과 실행 설정의 역할을 구분한다
- **내용**
  - [`AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md)의 역할: 저장소 구조, 코딩 규칙, 금지 사항, 빌드·테스트 명령, 완료 조건
  - `/init`으로 초안을 만든 뒤 사람이 검토해야 하는 이유
  - 전역 지침과 저장소 지침, 하위 디렉터리 지침의 계층 구조
  - 가까운 디렉터리의 지침이 더 구체적인 작업 규칙을 제공하는 방식
  - 좋은 `AGENTS.md`: 짧고 실행 가능하며 검증 명령이 명확한 문서
  - 나쁜 `AGENTS.md`: 장황한 철학, 서로 충돌하는 규칙, 존재하지 않는 명령, 비밀값 포함
  - [`config.toml`](https://learn.chatgpt.com/docs/config-file/config-basic)의 역할: 모델, 추론 수준, 샌드박스, 승인 정책, MCP 등 실행 설정
  - 지침과 설정을 구분하기
    - "테스트 후 결과를 보고하라" → `AGENTS.md`
    - "작업 공간 밖에는 쓰지 못한다" → `config.toml`의 샌드박스 설정
- **실습**: 실습 저장소에 `AGENTS.md`를 작성하고, 일부러 잘못된 규칙 하나를 넣어 Codex가 어떻게 따르는지 확인한 뒤 수정

## 4차시. Plan Mode·샌드박스·승인 — 안전하게 위임하기

- **목표**: 계획과 실제 실행을 분리하고, 작업 위험에 맞는 최소 권한을 선택한다
- **내용**
  - `/plan` 또는 읽기 중심 요청으로 구현 전 가정·영향 범위·검증 방법 확인
  - 계획 리뷰 기준: 요구사항 누락, 불필요한 범위 확대, 데이터 손실 가능성, 되돌리기 전략
  - [샌드박스](https://learn.chatgpt.com/docs/sandboxing)와 승인 정책은 서로 다른 안전장치
    - `read-only`: 탐색과 계획 중심
    - `workspace-write`: 작업 공간 안에서 수정과 일반 명령 허용
    - `danger-full-access`: 경계가 없는 고위험 모드이므로 격리된 환경과 명확한 이유가 있을 때만 사용
  - `untrusted`, `on-request`, `never` 승인 정책의 의미와 조합
  - 기본적으로 네트워크가 제한되는 이유, 설치·다운로드·외부 쓰기 전에 확인할 사항
  - 승인 요청을 읽는 법: 정확한 명령, 대상 경로, 외부 영향, 복구 가능성
  - 고위험 행동: 재귀 삭제, 강제 push, 운영 DB 변경, 대량 이동, 비밀값 접근, 외부 서비스 쓰기
  - [Codex 보안 지침](https://learn.chatgpt.com/docs/agent-approvals-security)에 따른 최소 권한 원칙
- **실습**: "이 폴더를 정리해 줘" 같은 위험한 요청을 Plan Mode에서 분석하고, 삭제 없는 계획으로 범위를 좁힌 뒤 안전한 권한으로 실행

## 5차시. 컨텍스트와 실행 환경 — 세션을 건강하게 유지하기

- **목표**: 컨텍스트 오염을 줄이고 작업 규모에 맞는 실행 환경을 선택한다
- **내용**
  - 컨텍스트에 포함되는 것: 대화, 읽은 파일, 명령 결과, diff, 지침, 도구 결과
  - 대화가 길어질수록 발생하는 문제: 오래된 가정 유지, 핵심 요구사항 매몰, 엉뚱한 파일 수정
  - `/status`로 현재 상태 확인, `/compact`로 긴 대화 압축, 새 작업은 새 대화로 분리
  - 한 대화에 한 가지 완료 목표를 두는 원칙
  - Work·로컬 CLI·IDE·클라우드 선택 기준

    | 상황 | 권장 환경 |
    |---|---|
    | 자료를 종합해 문서·발표자료·스프레드시트 등 완성된 업무 결과물 제작 | ChatGPT Work |
    | 저장소 탐색, 터미널 도구와 함께 빠르게 반복 | CLI |
    | 열린 파일이나 선택 코드의 집중 수정 | IDE 확장 |
    | 오래 걸리는 작업, 격리 필요, 여러 작업 병렬 처리 | Codex 클라우드 |
    | 반복 가능한 스크립트·CI 작업 | `codex exec` |

  - 로컬과 클라우드의 환경 차이: 설치된 도구, 환경 변수, 네트워크, 비밀값, 실행 재현성
  - 최신 정보가 필요한 작업과 저장소 내부 정보만으로 충분한 작업 구분
- **실습**: 하나의 제품 출시 요구사항을 조사·기획 문서·구현·테스트·발표자료로 나누고 각 작업을 Work·CLI·IDE·클라우드·비대화형 중 어디에 배치할지 결정한 뒤 근거 발표

## 6차시. Git/GitHub와 코드 리뷰 — 변경을 협업 가능한 단위로 만들기

- **목표**: 브랜치 생성부터 PR 리뷰까지의 흐름을 Codex와 함께 수행한다
- **내용**
  - 작업 시작 전 `git status`, `git diff`, `git log`로 기준 상태 확인
  - 사용자가 만든 기존 변경을 덮어쓰거나 임의로 되돌리지 않는 원칙
  - 변경을 작은 의미 단위로 나누고 커밋 메시지에 "무엇"과 "왜"를 남기기
  - 커밋 전 확인: 의도하지 않은 파일, 생성물, 비밀값, 디버그 코드
  - `/review`와 [Codex 코드 리뷰](https://learn.chatgpt.com/docs/code-review) 활용
  - 리뷰 요청 시 우선순위: 버그, 보안, 회귀, 테스트 누락, 유지보수성
  - `gh` CLI를 이용한 PR 생성, 리뷰 코멘트 반영, 최종 diff 재검토
  - Codex가 작성한 코드도 동일한 팀 리뷰 기준을 적용해야 하는 이유
- **실습**: 브랜치 생성 → 기능 구현 → 테스트 → `/review` → 커밋 → PR 생성 → 동료 리뷰 반영까지 한 사이클 수행

## 7차시. 테스트·검증·디버깅 — "됐습니다"를 증거로 바꾸기

- **목표**: Codex의 완료 보고와 실제로 검증된 결과를 구분한다
- **내용**
  - 검증의 4단계: 정적 검사 → 단위·통합 테스트 → 실제 실행 → diff와 로그 검토
  - 테스트 명령의 종료 코드와 전체 로그를 확인하는 습관
  - 새 테스트가 구현을 복제하거나 무조건 통과하지 않는지 검토
  - 버그 재현 패키지 만들기: 기대 동작, 실제 동작, 최소 재현 단계, 환경, 오류 전문
  - 실패 원인과 증상을 구분하고, 최소 수정으로 가설을 검증하는 디버깅
  - AI 생성 코드에서 자주 확인할 항목: 입력 검증, 인증·인가, 시크릿, 예외 처리, 동시성, 경계값, 의존성
  - 검증하지 못한 항목을 숨기지 않고 "미검증"으로 보고하게 하기
  - 에이전트가 같은 실패를 반복하거나 범위를 넓힐 때 멈추고 재계획하는 기준
- **실습**: 의도적으로 버그와 형식적인 테스트가 들어 있는 프로젝트를 Codex로 수정하고, 학생이 독립 검증 보고서 작성

## 8차시. Skills와 MCP — 반복 작업과 외부 도구 확장

- **목표**: 반복 가능한 절차를 Skill로 만들고, 필요한 외부 도구만 MCP로 연결한다
- **내용**
  - [`AGENTS.md`와 Skill의 차이](https://learn.chatgpt.com/docs/build-skills)
    - `AGENTS.md`: 저장소에서 항상 적용할 팀 규칙
    - Skill: 특정 종류의 요청에 재사용할 절차·참고자료·스크립트
  - Skill 기본 구조: 필수 `SKILL.md`, 선택 `scripts/`, `references/`, `assets/`
  - 좋은 Skill 설명: 언제 사용하고 언제 사용하지 않는지 명확하게 작성
  - `$skill-name` 또는 `/skills`를 통한 명시적 호출과 설명 기반 자동 선택
  - [MCP](https://learn.chatgpt.com/docs/extend/mcp)의 역할: Codex가 외부 데이터와 도구를 표준 방식으로 사용
  - `codex mcp add`, `codex mcp list`, `codex mcp login`, `/mcp`의 기본 흐름
  - 도구 연결 전 확인: 출처, 권한 범위, 읽기·쓰기 여부, 비밀값 저장 방식, 프롬프트 인젝션 위험
  - MCP는 "더 똑똑하게 만드는 장치"가 아니라 "할 수 있는 행동을 늘리는 연결"이라는 관점
- **실습**: 팀의 반복 작업 하나를 Skill로 만들고, 읽기 전용 MCP 서버 하나를 연결해 도구 목록과 승인 동작 확인

## 9차시. Subagents — 역할 분리와 병렬 작업

- **목표**: 독립적인 하위 작업을 병렬로 위임하고, 메인 에이전트가 결과를 통합하게 한다
- **내용**
  - [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)가 적합한 작업: 코드베이스 탐색, 여러 관점의 리뷰, 독립 모듈 조사, 테스트와 문서 분석
  - 병렬화하면 안 되는 작업: 같은 파일을 동시에 수정, 순서 의존 작업, 요구사항이 아직 불명확한 작업
  - 좋은 위임 단위: 목표·범위·산출물·금지 사항이 명확하고 독립적으로 완료 가능
  - 메인 에이전트의 역할: 요구사항 유지, 충돌 해결, 결과 교차 검증, 최종 통합
  - `/agent`로 실행 중인 에이전트 스레드 확인과 전환
  - Subagent가 메인 컨텍스트의 탐색 로그를 줄여 주는 장점과 토큰 사용량이 늘어나는 비용
  - 역할 예시: 탐색 담당, 구현 담당, 테스트 담당, 보안 리뷰 담당
- **실습**: 하나의 기능 요청을 탐색·테스트 설계·보안 리뷰로 나누어 병렬 위임하고, 결과를 근거와 함께 하나의 구현 계획으로 통합

## 10차시. 자동화 — `codex exec`, GitHub Action, CI

- **목표**: 대화형 사용을 넘어 재현 가능한 자동화 파이프라인을 설계한다
- **내용**
  - [`codex exec`](https://learn.chatgpt.com/docs/non-interactive-mode)로 스크립트와 CI에서 비대화형 실행
  - 기본 예: `codex exec "저장소 구조를 요약하고 위험 영역 5개를 알려 줘"`
  - stdout에는 최종 결과, stderr에는 진행 정보가 출력되는 구조
  - 자동화 기본값은 읽기 전용으로 시작하고 필요한 경우에만 `--sandbox workspace-write` 허용
  - `--json`의 JSONL 이벤트와 `--output-schema`를 이용한 기계 판독 가능한 결과
  - 자동화 프롬프트에 포함할 것: 고정 입력, 허용 범위, 실패 조건, 출력 스키마, 타임아웃과 재시도 정책
  - [Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)으로 PR 리뷰·릴리스 노트·이슈 분류 자동화
  - CI 비밀값 보호: 저장소가 제어하는 코드와 장기 API 키를 같은 실행 환경에 무분별하게 노출하지 않기
  - 자동화가 실패해도 배포·삭제 같은 고위험 단계로 넘어가지 않게 만드는 실패 폐쇄(fail-closed) 설계
- **실습**: 저장소 분석 결과를 JSON으로 출력하는 `codex exec` 예제를 만들거나, PR diff를 읽기 전용으로 검토하는 GitHub Actions 초안 작성

## 11차시. 캡스톤 — 검증 가능한 실전 미니 프로젝트

- **목표**: 브리핑, `AGENTS.md`, 계획, 권한, Git, 검증, 확장을 하나의 작업 흐름으로 통합한다
- **진행**
  - 개인 또는 팀별 프로젝트 선택
    - 기존 프로젝트 기능 추가
    - 버그 수정과 회귀 테스트
    - 반복 업무를 줄이는 CLI 도구
    - 작은 웹 또는 API 서비스
  - 요구사항과 완료 기준 작성 → `AGENTS.md` 작성 → Plan Mode로 설계
  - Git 체크포인트 → 구현 → 테스트·실행 검증 → `/review` → PR 작성
  - Skill, MCP, Subagents, `codex exec` 중 프로젝트에 필요한 확장 하나 이상 적용
  - 5분 발표 + 동료 코드 리뷰 + "Codex가 틀렸던 순간과 사람이 개입한 근거" 회고
- **필수 제출물**
  - 작업 브리핑과 완료 기준
  - `AGENTS.md`
  - 의미 단위의 커밋과 PR
  - 실행한 검증 명령과 결과
  - 권한·보안·미검증 항목을 포함한 회고
- **평가 기준**

  | 평가 영역 | 비중 | 확인 항목 |
  |---|---:|---|
  | 문제 정의와 브리핑 | 20% | 목표·범위·제약·완료 기준의 명확성 |
  | 안전한 위임 | 20% | 계획 검토, 최소 권한, 체크포인트, 승인 판단 |
  | 구현 품질 | 20% | 요구사항 충족, 코드 구조, 변경 범위의 적절성 |
  | 검증 품질 | 25% | 테스트, 실제 실행, 로그·diff 확인, 미검증 보고 |
  | 협업과 회고 | 15% | 커밋·PR 품질, 리뷰 반영, 한계와 개입 근거 |

| `/plan` | 다단계 작업을 실행 전에 계획하는 모드 전환 |
| `/review` | 미커밋 변경 또는 기준 브랜치 대비 코드 리뷰 |
| `/compact` | 현재 대화 컨텍스트 압축 |

| `/agent` | CLI에서 Subagent 스레드 확인·전환 |
| `codex mcp list` | 구성된 MCP 서버 목록 확인 |
| `codex exec "<task>"` | 비대화형 작업 실행 |

## 부록 B. 작업 위험도별 권장 운영 방식

| 위험도 | 예시 | 권장 방식 |
|---|---|---|
| 낮음 | 설명, 검색, 문서 초안 | 읽기 전용 또는 작업 공간 쓰기, 결과 확인 |
| 보통 | 기능 구현, 리팩터링, 테스트 수정 | 계획 검토, `workspace-write`, Git 체크포인트, 테스트 |
| 높음 | 의존성 추가, 외부 쓰기, 대량 파일 변경 | 명시적 승인, 대상·명령 확인, 작은 단계, 복구 계획 |
| 매우 높음 | 운영 DB, 배포, 비밀값, 강제 push, 재귀 삭제 | 격리 환경, 별도 검토자, 자동 실행 금지 또는 엄격한 정책 |

## 부록 C. Chat·Work·Codex 선택 기준

| 필요한 결과 | 먼저 선택할 환경 | 예시 |
|---|---|---|
| 답이나 아이디어 | Chat | 개념 설명, 아이디어 발산, 짧은 문장 다듬기 |
| 검토·편집 가능한 업무 결과물 | ChatGPT Work | 강의안, 조사 보고서, 발표자료, 스프레드시트, 정기 업데이트 |
| 실행·테스트된 코드 변경 | Codex | 기능 구현, 버그 수정, 리팩터링, 코드 리뷰, PR |
| 업무 결과물과 코드가 모두 필요 | Work와 Codex 연결 | Work로 요구사항·자료 정리 → Codex로 구현·검증 → Work로 보고서 작성 |

선택 기준은 도구 이름이 아니라 최종 산출물이다. 문서 안에 코드 조각이 있다는 이유만으로 Codex를 고르거나, 개발 프로젝트라는 이유만으로 모든 조사·발표자료 작업을 Codex에 맡기지 않는다.

## 강사용 참고

- 이 과정의 무게중심은 "더 많은 코드를 생성하기"보다 **작업을 정확히 정의하고, 권한을 제한하고, 증거로 검증하기**에 둔다.
- 4차시(계획·권한)와 7차시(검증)는 축소하지 않는다. 학생이 도구 사용법보다 판단 기준을 가져가는 핵심 차시다.
- 비개발자 또는 입문자 대상이라도 Git 체크포인트, diff 읽기, 테스트 결과 확인은 생략하지 않는다. 명령 암기보다 "되돌릴 수 있는 상태에서 맡긴다"는 원리를 먼저 가르친다.
- 모델명과 요금은 고정 암기시키지 않는다. 수업 시점에 `/model`, `/status`, 공식 문서를 확인하고 작업 복잡도·속도·비용·정확도의 균형으로 선택하게 한다.
- 클라우드, Subagents, MCP, GitHub Action은 계정·조직 정책에 따라 제공 범위가 다를 수 있다. 사용할 수 없는 환경에서는 설계 과제나 강사 데모로 대체한다.
- 학생 평가에서는 결과물의 화려함보다 브리핑, 승인 판단, 커밋 기록, 실제 테스트 로그, 미검증 항목 공개를 더 높게 평가한다.
